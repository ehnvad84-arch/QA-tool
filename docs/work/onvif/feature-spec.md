## Зачем — главная сессия

Первая настоящая польза инструмента: протокол соответствия ONVIF по 8 любым камерам с задачами программистам. Главный пробел готовых средств — выдача архива: камера с одним Profile S показывает картинку везде, но запись с SD-карты по ONVIF может не отдать. Этап проверяет профили S, G, M, T и **реально проигрывает архив**, а табу AD-7 действует и на сторонний onvif-tt.

## Поведение (BDD) — главная сессия

### S1: Проверки onvif-tt по любой камере
- **Дано** на стенде камеры любых производителей с ONVIF
- **Когда** в сценарии включён модуль ONVIF
- **Тогда** по каждой камере выполняются проверки onvif-tt (закреплённая версия), каждая — строка протокола со своим ID (`MEDIA2-1-1-4` и т. п.), обменом SOAP как доказательством и задачей программистам, если «не прошла»

### S2: Табу действует на onvif-tt
- **Дано** проверка onvif-tt (или любая будущая) пытается отправить запрещённую операцию (SetNetworkInterfaces, SetUser, SetSystemFactoryDefault…)
- **Когда** запрос идёт к камере
- **Тогда** он не доходит до камеры; проверка — «ошибка стенда: запрещённая операция не отправлена»; в протоколе видно, что именно было остановлено

### S3: Изменяющие и разрушающие проверки ONVIF — только по галочкам
- **Дано** сценарий без галочки «изменяющие»
- **Когда** идёт модуль ONVIF
- **Тогда** проверки onvif-tt, меняющие состояние (PTZ, изображение, запись), — «пропущена: не разрешено сценарием»; с галочкой — выполняются, настройки после модуля восстанавливаются (AD-3); перезагрузка — только с галочкой «разрушающие»

### S4: Матрица профилей
- **Дано** камера объявляет поддержку профилей (Scopes, GetServices)
- **Когда** модуль ONVIF закончен
- **Тогда** в протоколе раздел «Профили ONVIF»: для S, G, M, T — объявлен ли профиль, обязательные функции профиля по официальной спецификации (onvif/testspecs) и итог по каждой: поддержана и работает / не поддержана / не работает; объявленный, но не выполненный профиль — задача программистам

### S5: Выдача архива по Profile G
- **Дано** камера объявляет Profile G и на ней есть запись
- **Когда** выполняется `RUV-G-REPLAY-1`
- **Тогда** программа находит запись (FindRecordings → GetRecordingSearchResults), получает адрес воспроизведения (GetReplayUri) и **проигрывает не меньше 10 с архива**; «прошла» — кадры идут, время в потоке соответствует записи; иначе «не прошла» с причиной (отказ GetReplayUri, поток не открывается, нет кадров)

### S5a: На карте нет записей
- **Дано** камера объявляет Profile G, записей нет
- **Когда** в сценарии разрешены изменяющие проверки
- **Тогда** программа включает запись по ONVIF на 2 минуты (Recording Control: задание записи в режим Active или новое задание), затем проигрывает её как в S5 и возвращает задания записи в исходное состояние (решение директора 2026-11-03); не удалось включить запись — «не прошла» с причиной
- **Когда** изменяющие проверки не разрешены
- **Тогда** «пропущена: на карте нет записей, включить запись не разрешено сценарием»

### S6: Метаданные Profile M
- **Дано** камера объявляет Profile M
- **Когда** выполняются проверки `RUV-M-*`
- **Тогда** проверяется: конфигурация метаданных есть, поток метаданных открывается и в нём приходят кадры метаданных, модули аналитики перечисляются (только чтение)

### S7: SD-карта
- **Дано** камера сообщает о накопителе (GetStorageConfigurations или API адаптера)
- **Когда** выполняются проверки `RUV-SD-*`
- **Тогда** в протоколе: карта есть, объём и свободное место, запись идёт (по времени последних записей); форматирование — только с галочкой «разрушающие»
- *Уточнение при реализации (T12, 2026-11-03):* в ONVIF нет ни объёма и свободного места накопителя, ни операции форматирования (devicemgmt.wsdl: StorageConfigurationData — только тип, путь, адрес и учётная запись NAS). По ONVIF проверяются наличие накопителя (`RUV-SD-1`) и свежесть записи по часам камеры (`RUV-SD-2`); объём, место и форматирование с галочкой «разрушающие» переходят в адаптеры производителей (этап 3). В строке `RUV-SD-1` протокол прямо говорит, что объём по ONVIF не передаётся.

### S8: onvif-tt недоступен или упал
- **Дано** onvif-tt завис, упал или не установлен
- **Когда** идёт модуль ONVIF
- **Тогда** его проверки — «ошибка стенда» с причиной, остальные модули и камеры продолжают

## Вне рамок — главная сессия

- Проверки смены сети, учётных записей, сброса — табу (AD-7); onvif-tt `IPCONFIG-*`, `USER-*` и подобные исключаются списком.
- Официальная сертификация ONVIF (Declaration of Conformance).
- Адаптеры API производителей — этап 3 (SD-карта здесь — только по ONVIF).
- Глубокий разбор аналитики (сцены, точность детекторов) — этап 8.

## UI — ui-designer

Новых экранов нет. Экран «Сценарий»: модуль «ONVIF» с группами onvif-tt (по областям спецификации) и проверками `RUV-*`; в подсказке проверки — какой профиль она подтверждает. Протокол: новый раздел «Профили ONVIF» (таблица профиль × обязательная функция × итог) перед «Результатами проверок».

## Архитектура, API и данные — backend-architect

- `drivers/camera/taboo_proxy.py` — локальный HTTP-посредник на 127.0.0.1, по одному на камеру на время модуля: принимает запросы стороннего клиента, пересылает камере через `drivers/camera/http.request` (табу), запрещённое отклоняет SOAP Fault `ter:QAToolTaboo` и пишет в журнал; в ответах (GetServices, GetCapabilities, подписки событий) подменяет адреса служб камеры на адрес посредника — сторонний клиент не может обойти его, обратившись к XAddr напрямую (заодно закрывает N15: XAddr чужих хостов не используются). RTSP идёт к камере напрямую — это чтение потока.
- `checks/onvif/onvif_tt.py` — запуск onvif-tt отдельным процессом (`python -m qa_tool.checks.onvif.ott_runner`) против посредника; пароль — через переменную окружения процесса, не в командной строке (не виден в списке процессов); `--json-report` → наши CheckResult. Отображение статусов: passed → прошла, failed → не прошла, skipped → пропущена, xfailed → не прошла с пометкой «известная ошибка прошивки», error → ошибка стенда. Исключения по табу — список ID в `checks/onvif/excluded.py`. Тайм-аут модуля — из сценария.
- onvif-tt — зависимость с закреплённым коммитом 8866b25 (git); его корпус спецификаций в пакет не входит, прогону не нужен. Тест `DEVICE-3-1-11` меняет режим времени — восстановление снимком (T7).
- `checks/onvif/profiles.py` — матрица профилей: разбор `ONVIF_Profiles_Conformance_Device_Test_Specification.xml` (onvif/testspecs, закреплённый коммит, файл вендорится в `src/qa_tool/data/` с лицензией ONVIF) → обязательные функции S/G/M/T; итог по результатам проверок и ответам GetServices.
- `checks/onvif/replay.py` — `RUV-G-REPLAY-1`: ONVIF Search/Replay через `SoapClient`; проигрывание RTSP replay — ffmpeg (из сборки) с чтением 10 с; если камера требует заголовок `Require: onvif-replay`, которого ffmpeg не шлёт, — свой минимальный RTSP-клиент (DESCRIBE/SETUP/PLAY + счёт RTP-пакетов). Решение — по результатам T-исследования на живой камере.
- `checks/onvif/metadata.py`, `checks/onvif/storage.py` — `RUV-M-*`, `RUV-SD-*` через `SoapClient` (только чтение, кроме форматирования по галочке).
- Протокол: `report/model.py` + шаблоны — раздел «Профили ONVIF».

## Безопасность — backend-architect

- Табу на сторонний клиент: только через посредника; посредник слушает только 127.0.0.1, случайный порт, живёт на время модуля. Тест: onvif-tt-подобный клиент с SetUser через посредника — камера (mock) запрос не получила.
- Пароль камеры дочернему процессу — переменной окружения; в отчёте onvif-tt (`last_request`) секреты вырезаются `redact` до записи в базу.
- Ответы камеры (в том числе через onvif-tt JSON) — недоверенные данные: размер ограничен, разбор через json/defusedxml.

## Решения — главная сессия

| Вопрос | Выбрано | Почему | Отвергнуто |
|---|---|---|---|
| Как подключить onvif-tt | отдельный процесс + JSON-отчёт | его pytest/zeep не смешиваются с нашим процессом; зависание не валит прогон | импорт как библиотеки в рабочий процесс |
| Как удержать табу у стороннего клиента | локальный посредник с подменой XAddr | одна точка для onvif-tt сейчас и Playwright на этапе 5 | патч zeep-транспорта (только для zeep, хрупко при обновлении onvif-tt) |
| Пароль для onvif-tt | переменная окружения дочернего процесса | `--password` в командной строке виден в списке процессов | аргумент командной строки |
| Матрица профилей | официальная спецификация testspecs | корпус onvif-tt (2020) не знает Profile M | только объявленные камерой профили |
| Нет записей для проверки архива | программа сама включает запись на 2 мин и возвращает как было (изменяющая) | директор 2026-11-03 | готовит инженер заранее |
| Объём onvif-tt по умолчанию | все проверки; сузить можно в сценарии | директор 2026-11-03: больше находок, 8 камер параллельно — ~5 мин на стенд | только обязательные |
| Много результатов от одной проверки | составная проверка: результат несёт дочерние строки (по тесту onvif-tt), база и протокол пишут каждую строкой | ~150 тестов onvif-tt нельзя регистрировать заранее: состав зависит от камеры | отдельная регистрация каждого теста onvif-tt |
