## 1. Коротко

QA-tool подключается к IP-камере и проверяет, работает ли то, что камера заявляет по стандарту ONVIF. Итог — протокол на каждую камеру со списком задач программистам. Этап 2 добавляет проверки ONVIF. Веб-интерфейс, потоковые измерения и API производителей идут отдельными этапами и в этот PR не входят.

Главные риски, которые просим проверить:

1. **Ложная «прошла».** Программа не должна подтверждать то, что не проверила. Это главное правило проекта.
2. **Табу.** Программа никогда не меняет сетевые настройки, логины и пароли камеры.
3. **Посредник.** Сторонний клиент onvif-tt ходит к камере только через посредника, логин и пароль не должны уйти на чужой адрес.

## 2. Что сделано

- Подключён набор тестов [onvif-tt](https://github.com/OpenIPC/onvif-tt) закреплённой версии. Каждый тест становится строкой протокола.
- Посредник табу: вся работа onvif-tt с камерой идёт через него, запрещённые команды не доходят до камеры.
- Свои проверки: видеопоток, подписка на события, поиск записей, проигрывание архива, накопитель, метаданные.
- Матрица профилей: для объявленного камерой профиля сверяется каждая обязательная функция.
- Снимок и восстановление настроек вокруг изменяющих тестов.
- Поле `lan_address` для камер за туннелем и NAT.
- Виртуальная камера для тестов: SOAP и RTSP.

## 3. Как должно работать

Итог каждой строки протокола — один из четырёх:

| Итог | Значение |
|---|---|
| прошла | Проверка выполнена, есть доказательство |
| не прошла | Дефект камеры. Становится задачей программистам |
| пропущена | Проверку нельзя или не разрешено выполнять, причина названа |
| ошибка стенда | Сбой стенда или нет доказательства. Задачей программистам не становится |

| Проверка | Что делает | Ожидается |
|---|---|---|
| CORE-CONNECT-1 | Подключение и паспорт камеры, идёт всегда | При отказе во входе остальные проверки камеры «пропущена», вход не повторяется |
| ONVIF-TT | Запускает тесты onvif-tt | Строка на тест. Если не выполнен ни один тест — «ошибка стенда» |
| RUV-S-STREAM-1 | Читает видеопоток RTSP | Кадры идут не меньше 5 с, есть ключевой кадр |
| RUV-E-SUBSCRIBE-1 | Подписка на события: подписаться, продлить, отменить | Срок продлевается, после отмены подписки нет |
| RUV-G-SEARCH-1 | Поиск записей | Камера завершает поиск. Пустой список — не ошибка |
| RUV-G-REPLAY-1 | Проигрывает архив | Не меньше 10 с, есть ключевые кадры, время кадров внутри записи |
| RUV-SD-1, RUV-SD-2 | Накопитель и свежесть записи | Камера с записью сообщает о накопителе |
| RUV-M-* | Метаданные и аналитика, только чтение | Только для камер с Profile M |
| RUV-PROFILES-1 | Итог по профилям S, G, M, T | См. правила ниже |

Правила итога профиля:

- Профиль не объявлен — «пропущена».
- Обязательная функция сломана или не поддержана — «не прошла».
- Архив и поиск подтверждаются только своими проверками. Без них профиль G не получает «прошла». На камере без карты итог — «пропущена».
- onvif-tt не дал результатов — «ошибка стенда».

Табу: команды смены сети, учётных записей, сброса и импорта настроек не отправляются никогда, никакой галочкой. Изменяющие проверки идут только с галочкой «изменяющие» и после себя возвращают настройки.

## 5. Как проверить самому

Камеры не нужны: всё выполняется на виртуальной камере. Нужны Linux, [uv](https://docs.astral.sh/uv/), ffmpeg и Git. Для протоколов PDF нужна системная библиотека `libegl1`.

```bash
git clone https://github.com/ehnvad84-arch/QA-tool.git
cd QA-tool
git checkout 0c183238173d3cd13ef3ea9f043b68108c8d2fcf
uv sync
uv run pytest
```

Ожидается: 435 passed, около 4 минут.

Запуск виртуальной камеры, в отдельном терминале. Логин и пароль `admin`:

```bash
uv run python -m tests.mock_camera --count 1 --write-stand stand.yaml
```

Папка с результатами появится в `runs/`: откройте `protocol_1.html`.

### Сценарий A. Обычный прогон

```bash
QA_TOOL_PASSWORD_1=admin uv run qa-tool run --stand stand.yaml
```

Ожидается: `CORE-CONNECT-1`, `RUV-S-STREAM-1`, `RUV-E-SUBSCRIBE-1`, `RUV-G-SEARCH-1`, `RUV-SD-1` — прошла. `RUV-G-REPLAY-1` — пропущена, «на карте нет записей, включить запись не разрешено сценарием».

В сводке будет много «не прошла» (на момент проверки 63): виртуальная камера реализует только часть ONVIF. Это не дефект программы. Смотрите названные строки.

### Сценарий B. С изменяющими проверками

```bash
printf 'checks: [RUV-G-REPLAY-1]\nallow_writes: true\n' > scenario.yaml
QA_TOOL_PASSWORD_1=admin uv run qa-tool run --stand stand.yaml
rm scenario.yaml
```

Ожидается: `RUV-G-REPLAY-1` — прошла, около 2,5 минут. Программа включила запись, проиграла её и вернула режим записи.

### Сценарий C. Неверный пароль

```bash
QA_TOOL_PASSWORD_1=wrong uv run qa-tool run --stand stand.yaml
```

Ожидается: `CORE-CONNECT-1` — ошибка стенда, «камера не приняла логин или пароль». Остальные проверки — пропущена. Итог прогона «ошибка стенда», задач программистам нет.

## 6. Известные ограничения

Просим не заводить эти пункты как новые находки, но оценить, приемлемы ли они.

**Решения директора:**

- Ни одна настоящая камера не прошла `RUV-G-REPLAY-1`. Единственная камера с картой и службами архива, Dahua, отдала 7,8 с при пороге 10 с, поиск по времени у неё не работает. Директор принял задачу закрытой: способ проверки подтверждён, остальное — дефекты камеры.
- `RUV-SD-1` даёт «не прошла», если камера с записью не сообщает о накопителе. В том числе у камер без карты.
- Табу не ослабляется.
- Итог «пропущена» для профиля G на камере без карты выбран как осторожный.

**Не проверено:**

- Правки после прогонов 06.11 на настоящих камерах.
- Изменяющие проверки на настоящих камерах.
- Profile M на настоящих камерах: ни одна его не объявила.
- Запуск сборки на Windows на компьютере стенда. Тесты на Windows идут только в CI.
- Настоящие ответы камер MTOM, JPEG и страницы ошибок: проверены только на подставных ответах.

**Известные риски:**

- **Туннель без `lan_address` (С2).** Камера с адресом 127.0.0.1 может увести запрос с логином на другой порт компьютера стенда. Это подтверждено. При заполненном `lan_address` запросов нет. Работа через туннель без этого поля не допускается.
- **Ответы `multipart` отвергаются целиком.** Настоящую камеру с MTOM посредник не пропустит: итог «ошибка стенда». Если так ответят `GetServices` и `GetCapabilities`, строки профилей покажут ложное «не поддержана». В текстах ответов 06.11 признаков MTOM нет, но заголовки ответов не сохранялись.
- **Большой ответ (находка 62)** занимает поток посредника: 273 КБ — около 14 с. Страдает только процесс этой камеры.

**Отложенные находки:** 47, 57, 59, 60, 62, 67, 72, 73, С2. Описания в review.md и security-check.md. Находка №37 упомянута в журнале, но описания нет нигде.

**Не разобрано:** тесты onvif-tt `ANALYTICS-1-1-1`, `ANALYTICS-4-1-4`, `DEVICEIO-3-1-3`, `EVENT-3-1-12`. Часть из них может оказаться ложными провалами.
