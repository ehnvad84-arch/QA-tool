# Спецификация: stream

Статус: утверждена (Гейт 1, директор 05.11)
PRD: docs/PRD.md → требования 7 (поток) и 10 (кодеки)

## Зачем — главная сессия

Сейчас программа знает только, что поток открывается и кадры идут (`RUV-S-STREAM-1`, 5 секунд, первый профиль). Директору нужно видеть по каждой камере и каждому потоку: совпадает ли он с настройками, теряет ли пакеты и кадры, выдерживает ли долгую нагрузку, когда все камеры работают разом. Весь этап только читает поток: настройки камер не меняются, поэтому его можно сразу гонять на чужих камерах.

## Поведение (BDD) — главная сессия

### S1: параметры потока совпадают с настройками

- **Дано** камера с несколькими медиапрофилями, порог выборки 30 с
- **Когда** идёт сетевая фаза
- **Тогда** по каждому профилю в протоколе строка: кодек, разрешение, частота кадров, битрейт, длина GOP — заявлено и измерено; всё в допуске → «прошла». Постоянный битрейт сверяется в обе стороны, переменный — только сверху: `BitrateLimit` у него потолок, на тихой сцене поток меньше. Вид битрейта неизвестен → сверка только сверху

### S2: параметр вне допуска

- **Дано** камера заявляет 25 кадров/с, а отдаёт 15 (или битрейт, разрешение, кодек, GOP расходятся)
- **Когда** идёт проверка профиля
- **Тогда** строка «не прошла», в причине заявленное и измеренное значение, в протоколе — задача программистам

### S3: камера не сообщает настройки

- **Дано** Media1 отдаёт пустой кодировщик (так на Dahua с H.265, прогон QA-20261104-002), Media2 объявлен
- **Когда** программа читает настройки
- **Тогда** берутся настройки Media2; если их нет нигде, параметры только измеряются и печатаются, строка «пропущена» с причиной, а не «не прошла»

### S4: потери внутри камеры (TCP)

- **Дано** в потоке по TCP есть разрывы номеров RTP
- **Когда** идёт измерение
- **Тогда** «не прошла»: TCP сам ничего не теряет, значит, пакеты выбросила камера; в протоколе число и доля потерянных

### S5: потери и джиттер в сети (UDP)

- **Дано** камера отдаёт поток по UDP
- **Когда** идёт измерение
- **Тогда** потери и джиттер (RFC 3550) сравниваются с порогами, результат — отдельная строка по профилю

### S6: UDP не проходит

- **Дано** SETUP по UDP принят, но за 5 с не пришло ни пакета (брандмауэр компьютера стенда, туннель)
- **Когда** идёт измерение
- **Тогда** строка «пропущена: UDP не дошёл до стенда», это не ошибка камеры; отказ самой камеры (461) → «не прошла»: ONVIF требует RTP по UDP

### S7: пропуски кадров

- **Дано** промежуток между кадрами вдвое больше обычного для этого потока
- **Когда** идёт измерение
- **Тогда** кадры считаются пропущенными; доля выше порога → «не прошла», самый длинный промежуток в протоколе

### S8: поток не декодируется

- **Дано** выборка профиля H.264 или H.265 собрана в файл
- **Когда** ffmpeg её декодирует
- **Тогда** ошибки декодера → «не прошла» с их текстом; ffmpeg не найден → «ошибка стенда»; MJPEG — разрешение из заголовков RTP, строка декодирования «пропущена»

### S9: профиль не открывается

- **Дано** один из профилей не отдаёт поток
- **Когда** идёт проверка
- **Тогда** его строка «не прошла», остальные профили проверяются

### S9а: профилей больше, чем успевает проверка

- **Дано** у камеры профилей больше предела (8)
- **Когда** идёт проверка
- **Тогда** профили сверх предела «пропущены» с причиной, проверка заканчивается сама, планировщик её не снимает

### S10: стресс-тест

- **Дано** включён стресс-тест на 60 минут, 8 камер
- **Когда** наступает стресс-фаза
- **Тогда** все профили всех камер читаются одновременно весь срок; по камере и потоку — итог (потери, пропуски, обрывы, рост задержки) и таблица по минутам в доказательствах

### S18: вход Basic

- **Дано** камера предлагает для видео только вход Basic; если предложен и Digest, берётся Digest
- **Когда** идёт STREAM-PARAMS-1
- **Тогда** программа входит, проверки идут как обычно, строка STREAM-AUTH-1 «не прошла» с важностью «мелкая»: пароль уходит почти открытым (решение директора 2026-11-05)

### S11: обрыв в стресс-тесте

- **Дано** поток оборвался или молчит дольше 10 с
- **Когда** идёт стресс-тест
- **Тогда** программа переподключается и считает обрывы и время без потока; любой обрыв → «не прошла»; камера не вернулась за 3 минуты → остаток срока не ждём, итог по прошедшему времени, остальные камеры продолжают. Вернулся значит пришёл пакет: ответа на DESCRIBE мало. Время без потока — от последнего пакета до первого нового. Камера отвергла пароль (401; 403 на DESCRIBE или дважды подряд на удержании) → «ошибка стенда», ни одной новой попытки с этим паролем на этой камере ни в одной проверке с RTSP; потоки камеры открываются по очереди, поэтому одновременный обрыв не шлёт пароль от каждого

### S12: камера не держит все потоки разом

- **Дано** камера отказала в ещё одном одновременном потоке
- **Когда** стресс-тест открывает профили
- **Тогда** строка этого потока «не прошла» с кодом ответа и числом потоков, которые камера выдержала; остальные потоки продолжают

### S13: рост задержки

- **Дано** разница между меткой RTP и временем прихода растёт
- **Когда** идёт стресс-тест
- **Тогда** рост в худшем часе срока выше порога в секундах и выше порога скорости (с/ч) → «не прошла»: камера копит очередь. Один порог в секундах на сутках ловил бы уход часов камеры

### S14: стресс-тест выключен

- **Дано** галочка «Стресс-тест» в сценарии снята (по умолчанию)
- **Когда** идёт прогон
- **Тогда** проверка «пропущена: не разрешено сценарием», прогон не удлиняется

### S15: остановка оператором

- **Дано** идёт стресс-тест
- **Когда** оператор нажал «Стоп»
- **Тогда** потоки закрываются за 5 с, в протоколе итог за прошедшее время и пометка «прервано оператором»

### S16: секреты и табу

- **Дано** любой из сценариев выше
- **Когда** программа работает с камерой
- **Тогда** пароль только в заголовке Authorization, ни в командной строке, ни в файлах; RTSP-методы — только чтение (`check_rtsp`), ONVIF — только Get*

### S17: окно и справка

- **Дано** новый модуль «Поток»
- **Когда** оператор смотрит сценарий, прогон и протокол
- **Тогда** модуль подписан по-русски, у галочки подсказка, по F1 открывается раздел «Поток»

## Вне рамок — главная сессия

- SSIM и VMAF: перенесены в этап 7.
- Поиск застывшей или чёрной картинки: на неподвижной или тёмной сцене даст ложные срабатывания без оборудования стенда, это этап 7.
- Смена настроек кодировщика и проверка «задал → получил»: это запись в камеру, этап 7.
- Звуковые дорожки, многоадресная рассылка.

## UI — ui-designer

Новых экранов нет. Сценарий: галочка «Стресс-тест» рядом с длительностью; длительность недоступна, пока галочка снята. Прогон: строки модуля свёрнуты в счётчик, как у API. Подсказка и раздел F1 обязательны (автотест).

## Архитектура, API и данные — backend-architect

- `drivers/camera/rtsp.py`: `RtpPacket` получает номер и время прихода (`time.perf_counter`: у `monotonic` на Windows шаг около 15 мс при пороге джиттера 30 мс). Новый метод чтения с обратным вызовом, без накопления (`read_packets` рассчитан на короткую выборку, `rtsp.py:281`), со своим буфером приёма: после тайм-аута файл сокета непригоден (`rtsp.py:136`), а «Стоп» обязан срабатывать и на молчащей камере.
- Удержание: GET_PARAMETER раз в половину тайм-аута сессии из ответа SETUP. Ответ разбирается в том же цикле чтения: `_read_response` выбрасывает RTP (`rtsp.py:226`), и каждое удержание дало бы ложную потерю. Камера, не ответившая на удержание, чтение не останавливает.
- UDP: приём с адреса камеры, SO_RCVBUF не меньше 4 МБ (всплески ключевых кадров), пустой пакет на порт камеры перед PLAY: брандмауэр компьютера стенда пропускает ответы на исходящее.
- `drivers/camera/depacket.py` — RTP → Annex-B для H.264 и H.265, чистая логика. Параметры из `a=fmtp` (`sprop-*`) ставятся в начало выборки: `parse_sdp` их сейчас отбрасывает (`rtsp.py:339`), а часть камер шлёт SPS только в SDP. Разрешение измеряет ffprobe по выборке.
- `drivers/camera/onvif_generic.py`: все профили с настройками кодировщика, Media2 → Media1 (S3).
- `checks/stream/meter.py` — счётчик без сети: потери, кадры, частота, битрейт, GOP, джиттер, задержка, минутные срезы. Память постоянная.
- `checks/stream/params.py` (`STREAM-PARAMS-1`), `network.py` (`STREAM-NET-1`), `stress.py` (`STREAM-STRESS-1`) — составные проверки со строками по профилям, как `API-RUVER-1`: родитель всегда «прошла», итог в строках (`checks/api/ruver.py:845`), иначе `worker.py:179` выбросит строки у потерянной камеры.
- Время: срок планировщика снимает процесс и теряет все строки, поэтому `timeout_s` выводится из предела профилей (8) и выборки, у проверки свой предел меньше него, как `checks/api/ruver.py:96`. Стресс: срок = длительность + 3 мин S11 + запас на открытие и закрытие.
- Стресс: нити, по одному `RtspClient` на нить (`rtsp.py:12`): рабочий процесс `daemon`, дочерних процессов ему нельзя. Сбой нити становится строкой «ошибка стенда». 10 с и 3 мин переопределяются через `ctx.extra` для тестов.
- `core`: `Scenario.allow_stress`, `CheckContext.stress_minutes`, `CheckSpec.stress`: срок проверки = `timeout_s` + длительность (сейчас срок статический, `scheduler.py:181`, `:325`).
- Пороги — `thresholds` стенда, источник «стартовое значение»: `stream.sample_s` 30 с, `stream.bitrate_pct` ±20 %, `stream.fps_pct` ±10 %, `stream.gop_frames` ±1, `stream.udp_loss_pct` 0,1 %, `stream.jitter_ms` 30, `stream.drop_pct` 0,1 %, `stream.delay_growth_s` 1, `stream.delay_rate_s_h` 5. Потери TCP — всегда 0.
- Выборка для декодера — временный файл, удаляется после проверки; в доказательства не идёт (до 30 МБ на поток).

## Безопасность — backend-architect

Ответы камеры недоверенные: длины и типы пакетов RTP проверяются, пределы как в `rtsp.py:30`. ffmpeg получает только локальный файл, пароля и адреса камеры в его аргументах нет; запуск как `checks/onvif/onvif_tt.py:175` (`CREATE_NO_WINDOW`, utf-8), иначе на Windows всплывает окно консоли. Доказательства — через `core/secrets`. UDP-сокет принимает пакеты только с адреса камеры.

## Решения — главная сессия

| Вопрос | Выбрано | Почему | Отвергнуто |
|---|---|---|---|
| Как разбирать поток | свой RTSP-клиент, декодер на локальном файле | ffmpeg берёт пароль только в адресе, он виден в списке процессов | ffmpeg по rtsp:// |
| Потери | TCP и UDP отдельными строками | TCP прячет потери сети, UDP не проходит туннели | только один транспорт |
| SSIM и VMAF (директор 05.11) | этап 7 | нужны одна неподвижная сцена и смена битрейта в камере; без бокса цифры камер несравнимы | на этапе 4 |
| Стресс-тест (директор 05.11) | галочка, по умолчанию выключена | иначе обычный прогон длиннее минимум на 10 минут | включён всегда |
