## Зачем — главная сессия

Сейчас настройки изображения камер проверяют глазами в веб-интерфейсе: субъективно, долго, и ошибки прошивки (ползунок ничего не меняет или меняет не в ту сторону) доходят до заказчика. Нужно: для каждой камеры программа проводит каждую настройку изображения через положения 0 %, 50 % и 100 % её диапазона, снимает кадр в каждом и делает вывод «эффект есть / нет / обратный» по измеримой величине; затем сравнивает камеры между собой. Управляемого света и тестовых таблиц пока нет (этап 6 после этапов 7–9), но движок сразу готов принять их.

## Поведение (BDD) — главная сессия

Настройки этапа (закрытый список, 9 строк): яркость, контраст, насыщенность, резкость, баланс белого — усиление красного и синего отдельно, WDR, компенсация засветки, шумоподавление; каждая — если камера её объявляет в ONVIF Imaging. Положение «N %» — точка `min + N % × (max − min)` диапазона, который объявила сама камера.

### S1: настройка даёт эффект

- **Дано** камера объявляет настройку и её диапазон, галочка «изменяющие» включена, сцена неподвижна
- **Когда** программа ставит 0 %, 50 %, 100 % и в каждом положении снимает кадр
- **Тогда** величина настройки (по таблице правил) меняется в ожидаемую сторону на каждом шаге больше порога → «прошла», в протоколе три снимка и три значения

### S2: эффекта нет

- **Дано** как в S1
- **Когда** величина между 0 % и 100 % изменилась меньше порога
- **Тогда** «не прошла»: «настройка не меняет изображение», три снимка и значения в доказательстве

### S3: эффект обратный или неровный

- **Дано** как в S1
- **Когда** величина меняется в обратную сторону или между 0 % и 50 % и между 50 % и 100 % идёт в разные стороны
- **Тогда** «не прошла» с указанием, на каком шаге и куда

### S4: автоэкспозиция гасит эффект

- **Дано** у камеры включена автоматическая экспозиция, настройка из списка, на который она влияет (яркость, контраст, компенсация засветки, WDR)
- **Когда** эффекта нет
- **Тогда** «пропущена», а не «не прошла»; пояснение для инженера: что автоэкспозиция возвращает яркость кадра обратно, как выключить её вручную на камере и повторить, и что программа сама режим экспозиции не меняет

### S5: сцена нестабильна

- **Дано** перед настройкой программа дважды снимает кадр «до» без изменений
- **Когда** эти два кадра различаются больше порога (мигает свет, движение в кадре)
- **Тогда** настройка получает «ошибку стенда» с объяснением; задачи программистам нет

### S6: настройка не поддерживается или отвергнута

- **Дано** камера не объявляет настройку, или объявляет без диапазона
- **Тогда** «пропущена» с причиной
- **Дано** камера объявляет настройку, но отказывает в установке значения из своего же диапазона или читается другое значение
- **Тогда** «не прошла»: «камера не приняла значение из объявленного диапазона»

### S7: без галочки «изменяющие»

- **Дано** галочка выключена
- **Тогда** настройки не меняются, строки «пропущена: не разрешено сценарием»; снимок текущего кадра и текущие значения настроек всё равно попадают в протокол и сравнение

### S8: возврат настроек

- **Дано** проверка меняла настройки
- **Когда** она закончилась любым исходом, в том числе ошибкой
- **Тогда** все значения возвращены и сверены (AD-3); не вернулось → важность «блокер», в протоколе какая настройка, было, осталось

### S9: камера пропала посреди проверки

- **Тогда** «не прошла» по правилам планировщика (камера перестала отвечать), попытка вернуть значения при появлении; не вышло → S8

### S10: сравнение камер

- **Дано** в прогоне несколько камер
- **Когда** проверка картинки прошла у них
- **Тогда** отчёт сравнения: по каждой настройке снимки всех камер в положениях 0 %, 50 %, 100 % рядом, график величины по камерам и итог «эффект есть / нет / обратный»; камеры с разным диапазоном сравниваются по процентам диапазона, а не по абсолютным значениям

### S11: таблица правил

- **Дано** инженер хочет поменять порог или ожидаемую сторону для настройки
- **Тогда** он меняет её в конфигурации порогов без правки кода; в протоколе у каждой строки указан порог и его источник


## Вне рамок — главная сессия

- Экспозиция, ИК-фильтр, день/ночь, фокус и объектив — этап 6 (нужен свет и тёмная комната).
- Качество картинки по тестовым таблицам (резкость по ISO 12233, цвет по ColorChecker) — после этапа 6; движок готов принять «сцену с таблицей и светом».
- Запись настроек через веб-интерфейс и API адаптера — не в первой версии: только ONVIF Imaging.
- Режим экспозиции программа не меняет никогда, даже с галочкой: это меняло бы условия всех остальных настроек.

### 1. Экран «Сценарий»

Используется существующее дерево «модуль → группа → проверка»; новых виджетов, кроме одной подписи, нет.

```
Проверка                                            Фаза                Кому доступна
▾ ☑ Картинка
  ▾ ☑ Настройки изображения
      ☑ IMAGE-EFFECT-1 — Эффект настроек изображения   синхронная стенда   все производители
…
☐ Разрешить изменяющие проверки
     Без этой галочки «Картинка» только снимет текущий кадр и прочитает значения настроек:
     эффект настроек не проверяется, строки настроек будут «пропущена».          ← подпись, muted
☐ Разрешить разрушающие проверки
☐ Стресс-тест
```

- **Модуль** «Картинка» (`MODULE_TITLES["image"]` уже есть), подсказка общая: «Все проверки модуля «Картинка».».
- **Группа** «Настройки изображения» (`group`, `help_id="image"`). Группа нужна уже сейчас при одной проверке: на этапе 6 рядом встанет группа «Таблицы и свет» (`IMAGE-CHART-1`), и дерево не перестраивается.
- **Строка проверки**: «IMAGE-EFFECT-1 — Эффект настроек изображения», фаза «синхронная стенда», «все производители». F1 на строке → раздел справки `image`.
- **Описание** (оно же подсказка строки и столбец «Что делали» протокола), предлагаемый текст:
  «Настройки изображения из ONVIF Imaging — яркость, контраст, насыщенность, резкость, баланс белого (красный и синий), WDR, компенсация засветки, шумоподавление — по очереди ставятся в 0 %, 50 % и 100 % диапазона, который объявила камера. В каждом положении снимается кадр и измеряется величина; ожидается, что она меняется в нужную сторону на каждом шаге больше порога. После каждой настройки значение возвращается и сверяется. Режим экспозиции не меняется.»
  Подсказка строки добавляет через пустую строку (как `check_tooltip` добавляет профили): «Без галочки «изменяющие» настройки не меняются: снимается текущий кадр и читаются значения. Все камеры снимают одну сцену одновременно, около 6 минут. Только в цветовом боксе: во время съёмки не заходите в бокс и не меняйте свет.»

**Как пользователь понимает, что без галочки будут только снимки** — тремя способами, от заметного к подробному:

1. **Подпись под галочкой** «Разрешить изменяющие проверки» (`QLabel`, `role="muted"`, перенос строк). Видна, только если «Картинка» отмечена в дереве. Текст зависит от галочки:
   - снята: «Без этой галочки «Картинка» только снимет текущий кадр и прочитает значения настроек: эффект настроек не проверяется, строки настроек будут «пропущена».»
   - стоит: ««Картинка» будет менять яркость, контраст и другие настройки изображения и возвращать каждую после проверки. Режим экспозиции, сеть и пароли не меняются.»
   Обновляется в `_changed` и `refresh`. Подсказка подписи — тот же текст, F1 — `scenario-permissions`. Текст берётся из реестра проверки, а не пишется в экране: так же поведут себя onvif-tt, API и веб-обход, у которых тоже есть режим «только чтение» (см. вопрос 2).
2. **Подсказка галочки** дополняется: «… Без галочки часть проверок работает только на чтение: например, «Картинка» снимает текущий кадр и читает значения настроек.»
3. **Справка** `scenario-permissions` получает абзац о проверках, которые без галочки работают в режиме чтения.

**Место стенда.** Если место стенда сейчас «тёмная комната», строка серая (как недоступная по производителю) с подсказкой «Только в цветовом боксе: сейчас место стенда — тёмная комната. В прогоне строка будет «пропущена».». Это общее правило для всех проверок с `places`, правка в `ScenarioScreen.refresh`.

### 2. Окно «Прогон»

Проверка идёт 5–6 минут, все камеры разом, а её строки протокола приходят одной пачкой в конце (`_record` шлёт `children` после завершения). Без доработки строка хода 6 минут показывает «идёт», а процент места стоит. Поэтому три элемента:

```
┌ Прогон ───────────────────────────────────────────────────────────────────────────────┐
│ ┌ notice ────────────────────────────────────────────────────────────────────────────┐ │
│ │ Синхронная фаза: камеры снимают сцену бокса. Не заходите в бокс, не меняйте свет   │ │
│ │ и не двигайте камеры — иначе настройки получат «ошибку стенда».                    │ │
│ └────────────────────────────────────────────────────────────────────────────────────┘ │
│ Камеры     8 из 8 │ Место 3 · Dahua IPC-HFW2431 · прошивка 2.820                       │
│ Место 1 Рувер  ●  │ ┌ Ход проверки ─────────────────────────┐ ┌ Задачи программистам ┐ │
│ 40 % · ошибок нет │ │ 10:02 ● Связь с камерой и паспорт прошла│ │ …                    │ │
│ Место 2 Hikv…  ●  │ │ 10:03 ● onvif-tt: 161 тест        прошла│ │                      │ │
│ …                 │ │ 10:09 ● Эффект настроек изображения идёт│ │                      │ │
│                   │ │         Контраст · 50 % · настройка 2   │ │                      │ │
│                   │ │         из 9 · 1:40                     │ │                      │ │
└───────────────────┴─┴─────────────────────────────────────────┴─┴──────────────────────┴─┘
```

1. **Полоса-предупреждение** над списком камер и карточкой (`QFrame`, новая роль `notice`, текст `QLabel` с переносом). Видна, пока фаза прогона «синхронная стенда» и у хотя бы одного места есть идущая проверка (`RunView.phase` и `Step.state`, нового события не нужно). Текст общий для фазы, а не для «Картинки»: на этапе 6 в этой же фазе будет управляемый свет. Подсказка: «Камеры снимают одну и ту же сцену. Движение и смена света между кадрами дают «ошибку стенда» — проверка не засчитывается ни в плюс, ни в минус.»; F1 — `run-sync`. В блоке прогона слева (виден во всех разделах) к строке фазы добавляется «· не заходите в бокс».
2. **Строка хода составной проверки** — под названием вторая строка (`role="muted"`, 12 px, перенос): «Контраст · 50 % · настройка 2 из 9 · 1:40» — что сейчас снимается и сколько идёт. Нужен ход от процесса камеры, см. вопрос 1. Запасной вариант без события хода: «идёт 1:40 · строки протокола появятся в конце проверки» — время считает `RunView` от момента «started», для этого `Step` хранит время начала, а не только строку «ЧЧ:ММ».
3. **После окончания** — как у веба и потока: «Эффект настроек изображения: 11 строк», итог по худшей строке; в `Step.label` добавить префикс `IMAGE-` к формам «строка / строки / строк». Подсказка на названии — счёт итогов: «прошла 6 · не прошла 1 · пропущена 3 · ошибка стенда 1».

**Задачи программистам** — без изменений: «не прошла» по настройкам появятся карточками в конце проверки. Чтобы карточка читалась в общем списке, заголовки строк настроек — с названием модуля: «Картинка: яркость», «Картинка: возврат настроек» (это `ChildResult.title`; в протоколе получится «[IMAGE-BRIGHT-1] Картинка: яркость: настройка не меняет изображение»).

Превью потока в карточке («с этапа 4») этой фичей не меняется: показывать последний снимок «Картинки» в окне — не в первой версии.

### 3. Протокол камеры: «Приложение 1. Картинка: снимки и замеры»

**Где.** Отдельное приложение после раздела «4. Подписи», с новой страницы. Над подписями — строка «Приложения: 1 — Картинка: снимки и замеры.». Почему не раздел перед «Результатами проверок», как «Профили ONVIF»: девять настроек со снимками — 4–5 листов, они отодвинули бы результаты, задачи и подписи — то, что читает и подписывает ОТК. Снимки — доказательство, в документах ОТК это приложение. Если в прогоне нет строк `IMAGE-*`, приложения и строки о нём нет.

**Связь с основной таблицей.** Строки `IMAGE-*` остаются в «2. Результаты проверок» как есть. Столбец «Факт»: «0 % — 82,4; 50 % — 121,0; 100 % — 163,5 (средняя яркость, уровни 0–255)». Столбец «Доказательство»: путь папки и «· снимки — Приложение 1, п. 2». Причина «пропущена» по автоэкспозиции — коротко: «эффект погашен автоэкспозицией камеры — см. Приложение 1, пояснение А».

**Состав приложения** (макет `protocol-image.html`):

1. Вводная строка: сцена («обычная»), галочка «изменяющие», режим экспозиции камеры (и «программа его не меняет»).
2. **Возврат настроек** (`IMAGE-RESTORE-1`). Прошла — одна строка «Все значения возвращены и сверены». Не прошла — красная рамка в самом верху с таблицей «настройка · было · осталось» и указанием вернуть вручную: это блокер, его должны увидеть первым. Без галочки — «Ничего не менялось».
3. **п. 1 — Текущее состояние** (`IMAGE-STATE-1`): крупный снимок текущего кадра (≈ 120 мм) и таблица «настройка · текущее значение · диапазон камеры · положение в диапазоне, %», режим экспозиции, размер кадра и кодек. Без галочки (S7) это главное содержание приложения.
4. **Блоки настроек со снимками**, по одному на настройку, в порядке каталога. Блок — одна таблица: левая колонка (≈ 28 %, ≈ 75 мм) — итог, вид эффекта, пояснение одной-двумя фразами, величина и единица, ожидаемая сторона словом («растёт» / «уменьшается»), порог с источником, проверка сцены; три колонки — снимки 0 % / 50 % / 100 % (≈ 64 × 36 мм), под каждым: «величина 121,0 (+38,6)» и мелко «записано 50, прочитано 50». Шаг, который нарушил правило, выделен цветом «не прошла» и жирным. У «не прошла» — имена файлов выборок потока для программистов.
5. **Настройки без снимков** — одной таблицей «настройка · результат · причина»: не поддерживается, не разрешено сценарием, неверный диапазон, кадр не получен до первого снимка, сцена не подходит. Пустые рамки на полстраницы ради строки «не поддерживается» не печатаются.
6. **Пояснения** (А — автоэкспозиция; при необходимости Б — сцена не подходит), с новой страницы, одно на камеру, со списком настроек, к которым относится. Одно пояснение на камеру, а не в каждом блоке: автоэкспозиция гасит до трёх настроек сразу, текст повторялся бы трижды и ломал раскладку по 3 блока на лист.

**Пояснение А — текст** (решение директора: развёрнутый комментарий пользователю). Текст — шаблон отчёта по коду итога `skipped_ae`, а не причина из базы: причина в базе остаётся короткой.

> **Относится к:** {список настроек с ID}. Режим экспозиции камеры: {автоматический | камера не сообщила режим; программа считает его автоматическим, чтобы не выдать ложную задачу}.

> **Что произошло.** Камера сама держит яркость кадра постоянной: когда программа меняла настройку, автоматическая экспозиция подстраивала выдержку и усиление и возвращала картинку к прежней яркости. Поэтому по кадрам нельзя сказать, работает настройка или нет, и программа не считает это дефектом камеры: строка «пропущена», задачи программистам нет.
>
> **Как проверить вручную.**
> 1. Откройте веб-интерфейс камеры, раздел настроек изображения, подраздел экспозиции. Запишите текущий режим и значения выдержки и усиления.
> 2. Включите ручной режим экспозиции и задайте выдержку и усиление так, чтобы картинка была нормальной яркости.
> 3. В программе на экране «Сценарий» оставьте только модуль «Картинка», включите «Разрешить изменяющие проверки» и запустите прогон.
> 4. После прогона верните в камере режим экспозиции и значения, записанные в шаге 1.
>
> **Программа режим экспозиции не меняет никогда**, даже с галочкой «изменяющие»: он влияет на все остальные настройки изображения и на другие проверки.
>
> (если в списке есть компенсация засветки) Компенсацию засветки так не проверить: она работает только при автоматической экспозиции, а при ручной будет «пропущена: работает только с автоэкспозицией». Её проверка — на сцене с контровым светом (этап 6).

**Геометрия PDF** (A4 альбомная, поле 273 × 186 мм, как сейчас в `write_pdf`):

- блок настройки ≈ 52 мм → **3 блока на лист**, разрыв страницы перед каждым 1-м, 4-м, 7-м блоком задаётся в шаблоне явно (`page-break-before`): QTextDocument не умеет «не разрывать внутри»;

Кадр 4:3 или вертикальный «коридор» 9:16 уже, а не растянут; ячейка остаётся той же ширины;

**HTML.** Тот же шаблон, флаг формата при отрисовке (`media="html" | "pdf"`), а не `@media`: так поведение QTextDocument не надо угадывать. ### 4. Отчёт сравнения камер (S10)

**Как открыть.** Экран «Протоколы», таблица документов: строка «Сравнение картинки» сразу после «Сводного отчёта», столбец «Камера» — «все камеры (N)», «Заключение» — «настроек 9, камер N». Строка есть, только если файл `image_compare.html` существует (строки `IMAGE-*` хотя бы у двух камер). Те же кнопки PDF / Excel / HTML. Подсказка строки: «Снимки всех камер рядом в положениях 0, 50 и 100 % и график по каждой настройке.»; F1 — `protocols-files`. В сводном отчёте (`summary.html`) под матрицей — строка «Сравнение картинки со снимками и графиками — отдельный документ image_compare».

**Состав** (макет `compare-image.html`):

1. **Лист 1:** заголовок «СРАВНЕНИЕ КАМЕР: КАРТИНКА · прогон …», строка условий (место стенда, сцена, галочка «изменяющие», версия), абзац «камеры с разным диапазоном сравниваются по процентам диапазона», таблица камер (М1…М8 · камера · прошивка · № протокола · режим экспозиции · кадр) и **матрица итогов** «настройка × камера». В ячейке две строки: итог словом и вид эффекта коротко («эффект есть», «эффекта нет», «обратный», «неровный», «на части диапазона», «упор в пределы», «автоэкспозиция», «не поддерживается», «сцена менялась»); фон — заливки статусов из Excel. Последняя строка — «прошла N из 9». Обозначение «М3» = место 3, оно же в сетке и на графике.
2. **Лист на каждую настройку:** заголовок «Яркость · IMAGE-BRIGHT-1», строка «величина, единица, ожидаемая сторона, порог (источник)»; **сетка снимков** — столбцы камеры, строки 0 % / 50 % / 100 % и «Итог»; под каждым снимком «величина · записанное значение» (8 pt); ниже **график**.
3. **Без галочки (S7):** вместо листов настроек — плашка «Изменяющие проверки были запрещены сценарием: настройки не менялись, эффект не проверялся», текущие кадры камер (2 ряда по 4) и таблица «настройка × камера: текущее значение (положение в % от диапазона камеры)».

Камеры — столбцы, положения — строки, а не наоборот: при 8 камерах строк всего 3, и лист настройки вместе с графиком помещается на одну страницу A4; с камерами в строках 8 рядов снимков заняли бы весь лист без графика.

**Геометрия PDF для 1–8 камер** (поле 273 × 186 мм; колонка подписей 16 мм, на камеры 257 мм):

| Камер | Рамка миниатюры (Ш × В, 16:9) | Сетка (3 ряда + шапка + итог) | График | Лист целиком |
|---|---|---|---|---|
| 2–4 | 45 × 25 мм | ≈ 103 мм | 55 мм | ≈ 182 мм |
| 5 | 45 × 25 мм (257 / 5 − 3 = 48, ограничено 45) | ≈ 103 мм | 55 мм | ≈ 182 мм |
| 6 | 39 × 22 мм | ≈ 94 мм | 55 мм | ≈ 173 мм |
| 8 | 29 × 16 мм | ≈ 76 мм | 55 мм | ≈ 155 мм |

Правило: ширина рамки = min(45 мм, 257 мм / N − 3 мм); разрыв страницы перед каждой настройкой. Итого: 1 лист матрицы + 9 листов настроек = 10 листов. Миниатюра 480 px на 29 мм при 150 точек на дюйм (≈ 170 px) — с запасом. Если кадр не получен, на его месте серая рамка того же размера с текстом причины: сетка не «прыгает».

**График** (PNG из `report/charts.py`, QPainter, шрифт PT Sans из `gui/fonts` — одинаково на Windows и Linux):

- размер 1500 × 330 px (≈ 255 × 55 мм при 150 точек на дюйм); в HTML показывается шириной до 1000 px;
- ось X — «0 %», «50 %», «100 %» диапазона камеры; у камер с двумя положениями (WDR, компенсация засветки «вкл/выкл») точки только на 0 и 100 %, подписи «выкл» и «вкл» под осью;
- ось Y — величина с единицей («уровни 0–255»); у относительных величин — «% от значения в 0 %» и тонкая опорная линия на 100 %;
- линия на камеру; камеры различаются **цветом, значком точки и штрихом**, у правого конца линии подпись «М3» тем же цветом; у «не прошла» к подписи добавляется вид эффекта («М3 — эффекта нет»). Читается и в чёрно-белой печати — протокол ОТК часто печатают так;
- нет значения в положении — точки нет, линия обрывается; у камеры без данных линии нет, под графиком строка «Нет линии: М6 — пропущена (автоэкспозиция), М8 — ошибка стенда (сцена менялась)»;
- порог на графике не рисуется (у абсолютных величин у камер разная точка отсчёта), он в строке над сеткой.

**HTML** — тот же шаблон с флагом `media="html"`: миниатюры 150 px (8 × 150 + подписи ≈ 1300 px, помещается на 1366 px), снимок — ссылка на превью; сетка шире окна прокручивается внутри своей обёртки; у матрицы итогов ячейка — ссылка на лист настройки (якорь).

**Excel** `image_compare.xlsx`: листы «Камеры», «Итоги» (матрица настройка × камера, итог и вид эффекта, заливка статуса) и «Значения» (длинная таблица: настройка · место · камера · прошивка · диапазон · записано и величина в 0 / 50 / 100 % · единица · итог · причина · ссылки на снимки). Графики в Excel — не в первой версии: значения есть, инженер построит сам.

### 6. Слова итогов

Статус — только «прошла / не прошла / пропущена / ошибка стенда» (conventions.md); вид эффекта — вторым словом, из кода `Verdict.code`:

| Код | Вид эффекта | Пример причины |
|---|---|---|
| `effect` | эффект есть | «на шагах 0 → 50 % и 50 → 100 %: +38,6 и +42,5 при пороге 3,0» |
| `none` | эффекта нет | «настройка не меняет изображение: от 0 до 100 % изменение 0,8 при пороге 3,0» |
| `reverse` | эффект обратный | «величина уменьшилась на 25,1 от 0 до 100 %, ожидался рост» |
| `uneven` | эффект неровный | «на шаге 50 → 100 % величина уменьшилась на 6,2, ожидался рост» |
| `partial` | эффект на части диапазона | «на шаге 50 → 100 % изменение 1,1 при пороге 3,0» / с пометкой «упор в пределы сцены» |
| `skipped_ae` | погашен автоэкспозицией | «эффект погашен автоэкспозицией камеры — см. пояснение А» |
| `skipped_scene` | сцена не подходит | «в кадре нет пересвеченных и тёмных участков (0,2 % при нужном 1 %); нужна сцена этапа 6» |

Названия величин для ОТК (вместо формул): средняя яркость кадра; разброс яркости по кадру; насыщенность цвета; чёткость мелких деталей в центре кадра; отношение красного к синему; разница между светлыми и тёмными участками; яркость центра кадра; шум кадра во времени. Сторона: +1 — «растёт», −1 — «уменьшается». Числа — с десятичной запятой, по-русски.

### 9. Доступность

- У каждого нового элемента окна — подсказка и F1 (conventions.md): подпись под галочкой → `scenario-permissions`, полоса → `run-sync`, строка хода → `run-steps`, строка «Сравнение картинки» → `protocols-files`.

- Строка хода — текст, а не только полоска; полоса-предупреждение — текст, цвет лишь усиливает.
- Тексты от камеры (причины, Fault, имена профилей) — простым текстом (`plain`, `safe_tip`), в отчётах — автоэкранирование Jinja2, как сейчас.
- В отчётах статус всегда словом, цвет только дублирует; на графике камеры различаются тремя признаками и подписью; значения графика есть числами в сетке снимков — график не единственный источник.
- У каждого `<img>` — `alt`: «М3, яркость, 50 %: кадр камеры»; у рамки-заглушки — текст причины.
- Самый мелкий текст: значения под снимками сравнения — 8 pt, текст рамок-заглушек — 7 pt (только при 8 камерах).

### 12. Вопросы к главной сессии (ui-designer)

1. **Событие хода составной проверки.** Чтобы окно показывало «Контраст · 50 % · настройка 2 из 9», процессу камеры нужно сообщение `progress` (место, проверка, текст, сделано, всего) → `Event("progress")` → `RunView`. Это правка `worker.py` / `scheduler.py` (не чаще раза на снимок, ≈ 60 событий на камеру). Брать в эту фичу или обойтись запасным вариантом «идёт 1:40 · строки появятся в конце»? Пригодится и onvif-tt, и веб-обходу.
2. **Откуда текст «без галочки — только чтение».** Предлагается необязательное поле `CheckSpec` (например, `read_only_note`), чтобы экран «Сценарий» не знал о «Картинке» по ID. Решение — за backend-architect или планом; без поля текст придётся держать в экране.
3. **Статус «кадр не получен».** В «Кодах итогов» не сказано, что получает строка, если `StreamUnavailable` (нет видео, нет ключевого кадра за `keyframe_wait_s`) на одном из положений, когда кадры «до» были получены. Макет показывает «ошибка стенда»; если это «не прошла» (камера перестала отдавать видео после смены настройки — похоже на дефект), поменяются цвет и совет в рамке.
4. **Место раздела.** Принято: приложение после подписей. Если ОТК нужен раздел до «Результатов проверок» (как «Профили ONVIF»), блоки те же, меняется только место и разрывы страниц.

### Правило итогов `verdict()`

`s` = dir; `v0, v50, v100` (относительные — в % от v0); `D = s·(v100−v0)`, `d1 = s·(v50−v0)`, `d2 = s·(v100−v50)`; при «выкл/вкл» — только `D`.
1. Условие сцены не выполнено → «пропущена».
2. `|v100 − v0| < step` → нет эффекта: настройка «гасит» и экспозиция `AUTO` или не сообщена → «пропущена» (S4); иначе «не прошла» (S2).
3. `D ≤ −step` → «не прошла: обратный» (S3).
4. `d1 ≤ −step` или `d2 ≤ −step` → «не прошла: неровный», шаг и направление (S3).
5. `d1 ≥ step` и `d2 ≥ step` → «прошла» (S1).
6. Иначе → «не прошла: эффект на части диапазона», мелкая; пересвет или чернота в этом положении ≥ `clip_pct` → «прошла» с пометкой.

Порог строки — `step` с источником, `stability` и `dir` — в «ожидалось». `step ≤ stability` или `dir ∉ {+1, −1}` → «ошибка стенда: проверьте thresholds.yaml».

### Возврат и журнал (S8, S9)

- `SnapshotTaker.imaging(services, source_token, with_focus=False) -> Item`, сверка `"imaging"`: изменённые поля — с допуском, прочие — `canonical`; их расхождение — сведение в доказательстве, не блокер.

### Данные, секреты, табу

- Новых секретов нет: пароль из `keyring`, в ONVIF — только дайджестом, в RTSP — только в Authorization; в URL, аргументах ffmpeg, журнале и `measure.json` его нет. `onvif.txt` — через `redact`, текст Fault ≤ 300 символов через `scrub`.
- Кадры (в них может попасть человек у стенда) хранятся только локально. JPEG перекодирован из пикселей, метаданных камеры в нём нет; выборка потока — байты камеры как есть (SEI), её читает только ffmpeg.
- `SetImagingSettings`, `GetImagingSettings`, `GetOptions`, `GetProfiles`, `GetStreamUri` нет в `FORBIDDEN_ONVIF`; всё идёт через `SoapClient`. XML камеры при полной записи и возврате переразбирается и целиком проверяется `check_onvif`: вложенный `SetUser` → `TabooViolation`.
- RTSP — только `RTSP_READ_METHODS`, новых клиентов и сокетов нет (`tests/test_architecture.py` без исключений). Свои правила в коде: белый список полей, неизменность `Exposure`/`IrCutFilter`/`Focus`/`ImageStabilization`, запись только при `allow_writes`, снимок и возврат.
- Адреса только со стенда (`service_urls`, `to_stand_address`). Точек входа нет; аутентификация существующая, на отказ входа — без повтора.

### Враждебный ввод

| Ввод | Риск | Мера |
|---|---|---|
| огромное разрешение в SDP или потоке | память, время декодера | размер выхода ffmpeg задаёт наш фильтр; по ffprobe больше 8192 × 8192 или 0 → `FrameTooLarge`, «ошибка стенда» |
| бесконечный или плотный поток | диск, память | выборка ≤ 32 МБ и ≤ 300 кадров, срок `clip_s`, ffmpeg 20 с |
| поток, ломающий декодер | уязвимость ffmpeg | отдельный процесс со сроком, вход из временного файла, без адреса и пароля; версию ffmpeg в сборке ведём вручную (pip-audit её не видит) |
| диапазон: не число, NaN, ±∞, \|x\| > 10⁶, `min > max` | мусор в записи | проверка до вычисления положений, без записи |
| чтение назад — не число | ложное «прошла» | те же проверки → «не прошла» (S6) |
| токен источника > 64 символов или с разметкой | XML-инъекция | `escape()`; длиннее 64 (ReferenceToken) → «пропущена» |
| огромный ответ SOAP | память | XML ImagingSettings > 64 КБ → запись не начинается («ошибка стенда»); предел тела ответа в `http.py` — рекомендация для ядра |
| текст камеры в HTML и PDF | XSS, загрузка из сети | автоэкранирование Jinja2; `src` — только пути `evidence_dir` от `safe_name` внутри папки прогона; `QTextDocument` грузит только локальные файлы из `base_dir` |

Файлы: временные выборки — `qa-image-*` во временной папке (удаление в `finally` и при старте прогона); доказательства — `evidence/<место>/<ID>/` через `safe_name`; журнал — `runs/pending-image/<адрес>_<порт>.json`, атомарно с `fsync`; сравнение — `image_compare.*`, `compare/*.png`. Ни одно имя не строится из ответа камеры.

OWASP Top 10: A03 — экранирование XML и HTML; A06 — `numpy` в pip-audit, версия ffmpeg вручную; A08 — атомарный журнал. MITRE ATLAS не применим: ML нет, величины — формулы.

| Самая узкая версия (директор 07.11) | эффект каждой настройки без света и таблиц | принимается сразу, работает на любой камере | качество по таблицам; только снимки для глаз |

| Сравнение камер (директор 07.11) | входит в этап 7 по картинке | — | ждать этапа 9 |

| Изменяющая проверка | только с галочкой «изменяющие», снимок и возврат (AD-3) | never.md: камера не уходит со стенда изменённой | — |

| Обычная сцена без пересвета и шума | WDR, компенсация засветки, шумоподавление — «пропущена: нужна сцена этапа 6» | ложное «не прошла» хуже пропуска (never.md) | мерить на любой сцене |
| Контрольный кадр после возврата каждой настройки | да, +1 снимок, около +45 с на камеру | ловит изменение сцены во время проверки | без контроля |
| Камера не сообщает режим экспозиции | считать автоэкспозицию включённой (S4) | осторожный вариант: ложной задачи не будет | считать ручной |
| Картинка не успокоилась за 10 с, кадры «до» и «после» стабильны | «не прошла» | сцена доказанно стоит, колеблется камера | «ошибка стенда» |
| Журнал записи с прошлого прогона | как в веб-обходе: с галочкой вернуть, только если значение всё ещё наше; иначе блокер | одно правило для всех записей программы | только сообщать |
| Сохранение строк составной проверки при пропаже камеры | менять worker.py: строки не теряются; касается и веб-обхода | сейчас строка возврата и пройденные строки пропадают | оставить как есть |
| Баланс белого | две строки: усиление красного и синего | у них разные величины | одна строка |
| Набор настроек | закрытый список: 9 строк; ToneCompensation, Defogging и стабилизация — вне рамок | без сцены этапа 6 их эффект не измерить | «всё, что объявляет камера» |
| Ход проверки в окне «Прогон» | новое событие `progress` от процесса камеры, в этой фиче; пригодится onvif-tt и веб-обходу | 5–6 минут без хода выглядят зависанием | «идёт 1:40, строки появятся в конце» |
