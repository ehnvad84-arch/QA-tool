## Зачем — главная сессия

Сейчас настройки изображения камер проверяют глазами в веб-интерфейсе: субъективно, долго, и ошибки прошивки (ползунок ничего не меняет или меняет не в ту сторону) доходят до заказчика. Нужно: для каждой камеры программа проводит каждую настройку изображения через положения 0 %, 50 % и 100 % её диапазона, снимает кадр в каждом и делает вывод «эффект есть / нет / обратный» по измеримой величине; затем сравнивает камеры между собой. Управляемого света и тестовых таблиц пока нет (этап 6 после этапов 7–9), но движок сразу готов принять их.

## Поведение (BDD) — главная сессия

Настройки этапа (закрытый список, 9 строк): яркость, контраст, насыщенность, резкость, баланс белого — усиление красного и синего отдельно, WDR, компенсация засветки, шумоподавление; каждая — если камера её объявляет в ONVIF Imaging. Положение «N %» — точка `min + N % × (max − min)` диапазона, который объявила сама камера.

### S1: настройка даёт эффект

- **Дано** камера объявляет настройку и её диапазон, галочка «изменяющие» включена, сцена неподвижна
- **Когда** программа ставит 0 %, 50 %, 100 % и в каждом положении снимает кадр
- **Тогда** величина настройки (по таблице правил) меняется в ожидаемую сторону на каждом шаге больше порога → «прошла», в протоколе три снимка и три значения

### S2: эффекта нет

- **Дано** как в S1
- **Когда** величина между 0 % и 100 % изменилась меньше порога
- **Тогда** «не прошла»: «настройка не меняет изображение», три снимка и значения в доказательстве

### S3: эффект обратный или неровный

- **Дано** как в S1
- **Когда** величина меняется в обратную сторону или между 0 % и 50 % и между 50 % и 100 % идёт в разные стороны
- **Тогда** «не прошла» с указанием, на каком шаге и куда

### S4: автоэкспозиция гасит эффект

- **Дано** у камеры включена автоматическая экспозиция, настройка из списка, на который она влияет (яркость, контраст, компенсация засветки, WDR)
- **Когда** эффекта нет
- **Тогда** «пропущена», а не «не прошла»; пояснение для инженера: что автоэкспозиция возвращает яркость кадра обратно, как выключить её вручную на камере и повторить, и что программа сама режим экспозиции не меняет

### S5: сцена нестабильна

- **Дано** перед настройкой программа дважды снимает кадр «до» без изменений
- **Когда** эти два кадра различаются больше порога (мигает свет, движение в кадре)
- **Тогда** настройка получает «ошибку стенда» с объяснением; задачи программистам нет

### S6: настройка не поддерживается или отвергнута

- **Дано** камера не объявляет настройку, или объявляет без диапазона
- **Тогда** «пропущена» с причиной
- **Дано** камера объявляет настройку, но отказывает в установке значения из своего же диапазона или читается другое значение
- **Тогда** «не прошла»: «камера не приняла значение из объявленного диапазона»

### S7: без галочки «изменяющие»

- **Дано** галочка выключена
- **Тогда** настройки не меняются, строки «пропущена: не разрешено сценарием»; снимок текущего кадра и текущие значения настроек всё равно попадают в протокол и сравнение

### S8: возврат настроек

- **Дано** проверка меняла настройки
- **Когда** она закончилась любым исходом, в том числе ошибкой
- **Тогда** все значения возвращены и сверены (AD-3); не вернулось → важность «блокер», в протоколе какая настройка, было, осталось

### S9: камера пропала посреди проверки

- **Тогда** «не прошла» по правилам планировщика (камера перестала отвечать), попытка вернуть значения при появлении; не вышло → S8

### S10: сравнение камер

- **Дано** в прогоне несколько камер
- **Когда** проверка картинки прошла у них
- **Тогда** отчёт сравнения: по каждой настройке снимки всех камер в положениях 0 %, 50 %, 100 % рядом, график величины по камерам и итог «эффект есть / нет / обратный»; камеры с разным диапазоном сравниваются по процентам диапазона, а не по абсолютным значениям

### S11: таблица правил

- **Дано** инженер хочет поменять порог или ожидаемую сторону для настройки
- **Тогда** он меняет её в конфигурации порогов без правки кода; в протоколе у каждой строки указан порог и его источник


## Вне рамок — главная сессия

- Экспозиция, ИК-фильтр, день/ночь, фокус и объектив — этап 6 (нужен свет и тёмная комната).
- Качество картинки по тестовым таблицам (резкость по ISO 12233, цвет по ColorChecker) — после этапа 6; движок готов принять «сцену с таблицей и светом».
- Запись настроек через веб-интерфейс и API адаптера — не в первой версии: только ONVIF Imaging.
- Режим экспозиции программа не меняет никогда, даже с галочкой: это меняло бы условия всех остальных настроек.

### Обзор

Одна составная проверка `IMAGE-EFFECT-1` (модуль `image`, фаза «синхронная стенда», место — цветовой бокс) прогоняет по каждой настройке движок «настройка → способ записи → величина → правило» и отдаёт строки протокола через `CheckResult.children`. Родитель в протокол не попадает (урок этапа 5), поэтому итоги — отдельными строками: `IMAGE-STATE-1` (кадр и значения до проверки) и `IMAGE-RESTORE-1` (возврат и сверка).

Порядок для одной настройки:

1. Кадр «до» № 1, пауза `image.before_gap_s`, кадр «до» № 2. Если сцена нестабильна — «ошибка стенда» (S5).
2. Для 0 %, 50 % и 100 %: запись, чтение назад (S6), пауза применения, стабильный кадр, величина.
3. Возврат исходного значения этой настройки и контрольный кадр «после»: сцена за время настройки не менялась.
4. Правило выносит итог (S1–S4).

После всех настроек — полный возврат снимка ImagingSettings и сверка (S8). Между настройками каждая следующая стартует от исходного состояния: иначе контраст мерился бы при яркости 100 %.

### Решения

| № | Вопрос | Выбрано | Почему | Отвергнуто (цена) |
|---|---|---|---|---|
| A1 | Фаза прогона | `Phase.SYNC`, `places={COLOR_BOX}`; `resources` сейчас пустые, на этапе 6 — `{"light"}` | все камеры снимают одну сцену в одно время, поэтому сравнение честное, а на этапе 6 свет держится заблокированным на весь прогон картинки без переноса проверки в другую фазу | NETWORK — проще, но этап 6 потребует переноса и сменит порядок протокола; SEQUENTIAL с блокировкой сцены — честно, но в 8 раз дольше (≈ 45 мин вместо 6) |
| A2 | Галочка «изменяющие» | спека с `writes=False`, решение внутри по `ctx.allow_writes`, как у onvif-tt, API и веб-обхода | S7 требует строк «пропущена» по каждой настройке и снимка текущего кадра; `writes=True` дал бы одну строку «пропущена» | `writes=True` (теряем S7); две регистрации (кадр отдельно, эффект отдельно) — экран «Сценарий» усложняется, выигрыша нет |
| A3 | Форма записи | сначала `SetImagingSettings` только с меняемым элементом; на отказ (Fault, не вход и не связь) — один повтор полным блоком из снимка с одним изменённым полем; `ForcePersistence=false` на шагах, `true` — на финальном возврате | частичная запись не трогает экспозицию и ИК-фильтр вовсе; полный блок — путь, уже проверенный `SnapshotTaker` на камерах этапа 2; без сохранения во флеш перезагрузка сама возвращает исходное (S9) | только полный блок — у части камер есть поля только для чтения, они отвергли бы запись; только частичная — ложные «не приняла» на камерах, которые требуют полный блок |
| A4 | Кадр | новая RTSP-сессия на каждый снимок: DESCRIBE/SETUP/PLAY → с ключевого кадра `image.clip_s` → TEARDOWN | переиспользует `start_video` и `Sampler`; каждый кадр гарантированно после смены настройки | постоянная сессия с кольцевым буфером группы кадров — быстрее на ≈ 1 с на снимок, но новый код чтения в фоне и риск закрытия сессии камерой; снимок по HTTP отвергнут директором |
| A5 | Вычисления | `numpy` — новая прямая зависимость | все величины — несколько строк над массивами; ≈ 20 МБ в установщике | OpenCV (`opencv-python-headless`) — 60–90 МБ ради Лапласиана и HSV; scikit-image тянет scipy; только фильтры ffmpeg (`signalstats`) — нет масок и Лапласиана, разбор текстового вывода зависит от версии ffmpeg |
| A6 | Таблица правил | плоские ключи в существующем `thresholds.yaml`: `image.<настройка>.step`, `.stability`, `.direction`; стартовые значения — в `rules.py` | работает текущий `load_thresholds` (значение, единица, источник), источник печатается в протоколе (S11), новый файл не нужен ни окну, ни командной строке | отдельный `image_rules.yaml` — свой загрузчик, путь в окне, CLI и `WorkerArgs`; направление числом `+1/−1` — цена выбранного варианта: читается хуже слова |
| A7 | Где лежат замеры | файл `measure.json` в папке доказательств строки (по образцу `matrix.json` у RUV-PROFILES); база без миграций | протокол и отчёт сравнения читают его так же, как матрицу профилей; старые прогоны открываются без изменений | новая таблица SQLite — миграция и режим только чтения для старых баз |
| A8 | Доказательства-картинки | байты в `Evidence` (через очередь процессов), размер ограничен: превью ≤ 1280 px и миниатюра 480 px в JPEG; полные данные — только для «не прошла», и это выборка потока, а не PNG | один писатель папки прогона (координатор) сохраняется; выборка потока точнее PNG и меньше: 2 с при 8 Мбит/с ≈ 2 МБ против 12–20 МБ PNG 4K | файлы в промежуточной папке с переносом координатором — меньше памяти, но новый вид доказательства и проверка путей; PNG полного размера для всех кадров — до 6 ГБ на прогон |
| A9 | Журнал записи | общий модуль `core/write_journal.py` (атомарная запись JSON и `fsync` — вынести из `web_journal.py`), своя папка `pending-image/`, своя строка `IMAGE-WRITE-LOST`; планировщик проходит по списку журналов | один файл на камеру у веба и картинки затирал бы чужую запись; код атомарной записи не дублируется | копия `web_journal.py` — дубль; общий файл на камеру — потеря записи веб-обхода |

Предложение для общего уровня (→ architecture.md, решение принимает главная сессия): в стеке `CLAUDE.md`/`AGENTS.md` указаны OpenCV и scikit-image, а в `pyproject.toml` их нет. Вычисления над кадрами — `numpy`; OpenCV и scikit-image не подключаем, пока нет задачи, которой не хватает `numpy`.

### Каталог настроек

Положение `N %` — `min + N % × (max − min)` из `GetOptions`. Если обе границы целые, значение округляется до целого: часть камер отвергает `50.5`. Чтение назад совпадает, если разница не больше `max(0,5 % диапазона, 1e-6)`.

| Строка | Настройка | Поле ImagingSettings20 (запись) / ImagingOptions20 (диапазон) | Как ставится положение |
|---|---|---|---|
| `IMAGE-BRIGHT-1` | яркость | `Brightness` / `Brightness` Min–Max | число |
| `IMAGE-CONTRAST-1` | контраст | `Contrast` / `Contrast` | число |
| `IMAGE-SAT-1` | насыщенность | `ColorSaturation` / `ColorSaturation` | число |
| `IMAGE-SHARP-1` | резкость | `Sharpness` / `Sharpness` | число |
| `IMAGE-WB-1` | баланс белого, красный | `WhiteBalance` (`Mode=MANUAL`, `CrGain`) / `WhiteBalance.YrGain` | второе усиление держится на 50 % своего диапазона |
| `IMAGE-WB-2` | баланс белого, синий | `WhiteBalance` (`Mode=MANUAL`, `CbGain`) / `WhiteBalance.YbGain` | то же |
| `IMAGE-WDR-1` | WDR | `WideDynamicRange` (`Mode=ON`, `Level`) / `Mode`, `Level` | уровень при `ON`; без диапазона уровня — см. «Решения» |
| `IMAGE-BLC-1` | компенсация засветки | `BacklightCompensation` (`Mode=ON`, `Level`) / `Mode`, `Level` | то же |
| `IMAGE-NR-1` | шумоподавление | `Extension/Extension/Extension/NoiseReduction/Level` / `Extension4/NoiseReductionOptions/Level` (флаг) | диапазон 0…1 задан спецификацией ONVIF, камера объявляет только поддержку |

Баланс белого — две строки, поэтому настроек 9, а не 8. Усиления красного и синего — разные регуляторы, и ошибка прошивки бывает в одном из них.

**Белый список записи.** `ImagingWriter` отправляет только перечисленные поля. Уходящий блок `Exposure`, `IrCutFilter`, `Focus` и `ImageStabilization` при полной записи побайтно совпадает со снимком (`canonical`), иначе — `ImageWriteRefused` до отправки. Режим экспозиции программа не меняет (рамки фичи) — это правило в коде, а не только в документе.

### Величины и стартовые правила

Кадр декодируется в два вида: рабочий (весь кадр, ширина 1280 px) и центральный фрагмент родного разрешения до 1280 × 720. Яркость Y = 0,2126 R + 0,7152 G + 0,0722 B (BT.709), уровни 0–255. Пересвет — Y ≥ 250, чернота — Y ≤ 5.

| Настройка | Величина | Вид кадра | Единица | `direction` | `step` | `stability` | Гасит АЭ |
|---|---|---|---|---|---|---|---|
| яркость | средняя Y | рабочий | уровень | +1 | 3,0 | 1,0 | да |
| контраст | СКО Y | рабочий | уровень | +1 | 2,0 | 0,7 | да |
| насыщенность | средняя (max−min)/max по пикселям с max(R,G,B) в 16…249 | рабочий | % | +1 | 2,0 | 0,5 | нет |
| резкость | дисперсия Лапласиана 3 × 3 по Y | центральный, родное разрешение: уменьшение смазало бы ореолы повышения резкости | % от значения в 0 % | +1 | 10 | 3 | нет |
| ББ красный | R/B: отношение средних R и B по пикселям, где все каналы в 16…249 | рабочий | % от значения в 0 % | +1 | 3 | 1 | нет |
| ББ синий | R/B, как выше | рабочий | % от значения в 0 % | −1 | 3 | 1 | нет |
| WDR | разрыв «свет − тень»: средняя Y по маске 10 % самых светлых минус средняя по маске 10 % самых тёмных; маски берутся из кадра «до» № 1, сцена неподвижна | рабочий | уровень | −1 | 4,0 | 1,0 | да |
| компенсация засветки | средняя Y центральной трети кадра | рабочий | уровень | +1 | 3,0 | 1,0 | да |
| шумоподавление | временной шум: СКО Y каждого пикселя по 8 соседним кадрам, медиана по фрагменту | центральный, родное разрешение: уменьшение усредняет шум | % от значения в 0 % | −1 | 10 | 5 | нет |

Предусловия сцены (иначе строка «пропущена» с причиной и подсказкой «нужна сцена этапа 6»):

- WDR и компенсация засветки — в кадре «до» пересвет и чернота вместе занимают не меньше `image.wdr_scene_clip_pct` = 1 %;
- шумоподавление — временной шум в положении 0 % не меньше `image.nr_noise_floor` = 0,5 уровня.

Все стартовые значения имеют источник «стартовое значение: уточнить по эталонным камерам» (PRD, ответ директора 5).

**`verdict()`** — чистая функция. Обозначения: `s` — direction; `v0`, `v50`, `v100` — значения величины (для относительных величин — в % от `v0`, знаменатель не меньше малой константы величины); `D = s·(v100 − v0)`, `d1 = s·(v50 − v0)`, `d2 = s·(v100 − v50)`.

1. Предусловие сцены не выполнено → «пропущена» (сцена).
2. `|v100 − v0| < step` → «нет эффекта». Если настройка зависит от АЭ, а экспозиция `AUTO` или режим не сообщён → «пропущена» с пояснением S4. Иначе → «не прошла» (S2).
3. `D ≤ −step` → «обратный», «не прошла» (S3).
4. `d1 ≤ −step` или `d2 ≤ −step` → «неровный», «не прошла» с указанием шага и направления (S3).
5. `d1 ≥ step` и `d2 ≥ step` → «прошла» (S1).
6. Иначе (один шаг меньше порога, обратного хода нет) → «эффект на части диапазона». Если в этом положении пересвет или чернота занимают не меньше `image.clip_pct` = 5 % — «прошла» с пометкой «упор в пределы сцены»; иначе — см. «Решения».

Порог строки протокола (`CheckResult.threshold`) — `step` с его источником; `stability` и `direction` пишутся в «ожидалось». Если `step ≤ stability` или `direction ∉ {+1, −1}`, все строки настроек получают «ошибка стенда: проверьте thresholds.yaml».

### Формат правил в `thresholds.yaml`

```yaml
image.brightness.step:      {value: 3.0, unit: "уровень", source: "эталон Рувер IPC-…, прогон QA-20261120-002"}
image.brightness.stability: {value: 1.0, unit: "уровень", source: "стартовое значение: уточнить по эталонным камерам"}
image.brightness.direction: {value: 1,   unit: "направление", source: "ONVIF Imaging: больше — светлее"}
image.wb_blue.direction:    {value: -1,  unit: "направление", source: "рост синего уменьшает R/B"}
image.apply_delay_s:        {value: 1.5, unit: "с", source: "стартовое значение"}
```

Ключи настроек: `brightness`, `contrast`, `saturation`, `sharpness`, `wb_red`, `wb_blue`, `wdr`, `blc`, `nr`. Чего нет в файле — берётся из `rules.DEFAULTS`. Какая величина у настройки — решение кода: новая величина требует кода, а порог и направление — нет (S11).

### Стабильный кадр после смены настройки

| Ключ | Старт | Почему |
|---|---|---|
| `image.apply_delay_s` | 1,5 с | процессор изображения применяет настройку за 1–3 кадра, а WDR и автоэкспозиция сходятся до ≈ 1 с |
| `image.keyframe_wait_s` | 12 с | «умные» кодеки (H.264+, Smart GOP) дают группу кадров до 8–10 с |
| `image.clip_s` | 2,0 с | выборка на один снимок после ключевого кадра: 50 кадров при 25 к/с |
| `image.settle_frames` | 5 кадров | окно, в котором проверяется, что картинка успокоилась |
| `image.settle_luma` | 1,0 уровня | размах средней Y в окне: меньше — кадр стабилен |
| `image.settle_max_s` | 10 с | дольше — картинка не установилась (см. «Решения») |
| `image.before_gap_s` | 1,0 с | промежуток между двумя кадрами «до»: ловит мигание и движение |
| `image.scene_diff` | 3,0 уровня | средняя абсолютная разница серых рабочих кадров «до» № 1 и № 2, а также «до» и «после» |
| `image.reconnect_wait_s` | 120 с | типичная перезагрузка камеры занимает 60–90 с (S9) |

Алгоритм: после записи — пауза `apply_delay_s`, затем сессия RTSP и выборка `clip_s` с ключевого кадра. ffmpeg декодирует её потоком, а в памяти держится кольцо последних 8 кадров. Если последние `settle_frames` кадров укладываются в `settle_luma`, берутся последний кадр (величины) и последние 8 (шум). Иначе читается следующая выборка, пока не истечёт `settle_max_s`.

Вызов ffmpeg — один на снимок: выход rawvideo rgb24, где рабочий кадр и центральный фрагмент склеены по вертикали. Размер выхода задаёт наш фильтр, а не камера, поэтому память на кадр известна заранее (≈ 5,5 МБ). Превью и миниатюру кодирует в JPEG второй вызов ffmpeg из выбранного кадра. Метаданные камеры в JPEG не попадают: картинка закодирована заново из пикселей.

### Снимок и возврат (AD-3, S8, S9)

- `SnapshotTaker` получает публичный метод `imaging(services, source_token, with_focus=False) -> Item` и способ сверки `"imaging"`: меняемые поля сравниваются с допуском чтения назад, остальное — `canonical`. Расхождение в полях, которые проверка не меняла, пишется в доказательство как сведение, блокером не становится: значения экспозиции у части камер плавают сами.
- Перед первой записью — журнал (`intent`), затем `sent` → `restoring` → удаление после сверки. В журнале: прогон, место, адрес, порт, токен источника, исходный XML ImagingSettings (≤ 64 КБ), настройка и записанное значение.
- Камера пропала (S9): цикл настроек прекращается, раз в 5 с проверяется `camera_alive`, ожидание — до `image.reconnect_wait_s`. Камера вернулась → полный возврат и сверка; строка текущей настройки — «не прошла: камера перестала отвечать», оставшиеся — «ошибка стенда: проверка прервана». Камера не вернулась → журнал остаётся, `IMAGE-RESTORE-1` — блокер «значения не возвращены, камера не отвечает».
- Процесс камеры снят планировщиком (зависание): строку `IMAGE-WRITE-LOST` (блокер) пишет `Runner._report_lost_write` из журнала — по образцу `WEB-WRITE-LOST`.
- Журнал прошлого прогона при старте проверки — см. «Решения»; рекомендуется «сравнить и вернуть»: вернуть только поля, которые всё ещё равны записанному нами значению.

**Изменение ядра.** `worker.py` при пропаже камеры заменяет результат одной строкой `LOST_DURING_CHECK` и теряет `children`, а с ними — строки возврата. Для составных проверок строки нужно сохранять и отправлять как есть. Затрагивает и веб-обход.

### Данные: доказательства, объём, протокол, сравнение

Папка строки: `runs/<прогон>/evidence/<место>/<ID строки>/`. Имена файлов задаёт программа, а не камера:

- `before1.jpg`, `before2.jpg`, `p000.jpg`, `p050.jpg`, `p100.jpg`, `after.jpg` — превью ≤ 1280 px, JPEG q85, ≈ 150–250 КБ;
- те же имена с `_t` — миниатюры 480 px, ≈ 30–50 КБ, для PDF и сеток;
- `clip_p000.h264|.h265` и т. д. — выборки потока, только у строк «не прошла»;
- `onvif.txt` — обмен SOAP по настройке, секреты вырезает `RunStore`;
- `measure.json`.

Схема `measure.json` (версия 1):

| Счёт | Кадров на прогон | Превью и миниатюры |
|---|---|---|
| по формуле задачи: 8 камер × 8 настроек × (3 положения + 2 «до») | 320 | ≈ 80 МБ |
| с каталогом выше: 8 × (1 `STATE` + 9 × (2 «до» + 3 + 1 «после»)) | 440 | ≈ 105 МБ |

Выборки потока для «не прошла» — 1–4 МБ на положение, в худшем случае (всё не прошло, 4K) ≈ 0,9 ГБ. SSD стенда — 1 ТБ (equipment.md). Через очередь процессов одна камера передаёт ≈ 13 МБ, в худшем случае ≈ 120 МБ.

Протокол камеры:

- новый раздел «Картинка» по образцу матрицы профилей: `Protocol.image` собирается из `measure.json` строк модуля `image`;
- на настройку — три миниатюры 0/50/100 %, значения, порог с источником, итог;
- HTML ссылается на превью относительными путями;
- `write_pdf` получает параметр `base_dir` (папка прогона), иначе `QTextDocument` не найдёт картинки по относительным путям;
- Excel — значения и относительные ссылки на превью без вставки картинок: openpyxl для картинок требует Pillow, а он у нас только транзитивный.

Отчёт сравнения (S10) — отдельные файлы `image_compare.html/.pdf/.xlsx` в папке прогона, выпускаются из `publish()`, если строки `IMAGE-*` есть хотя бы у двух камер:

- `report/image.py` строит `ImageComparison`: для каждой настройки строки камер (место, модель, прошивка, итог, код итога, три значения, три миниатюры, объявленный диапазон);
- `report/charts.py` рисует график PNG средствами Qt (QPainter, без matplotlib) в `runs/<прогон>/compare/`;
- по оси X — 0/50/100 % диапазона камеры; абсолютные величины — как есть (единица общая), относительные — в % от значения камеры в 0 %;
- без галочки — только кадры `IMAGE-STATE-1` и текущие значения.

Модуль сделан так, чтобы общий отчёт сравнения этапа 9 включил его как раздел.

### Сцена этапа 6

- Метрики берут области из `Scene.regions`. «Обычная» сцена отдаёт весь кадр и центр, «таблица» — патчи ColorChecker и мишени eSFR, поэтому движок не меняется.
- На этапе 6 сцена «таблица и свет» регистрируется отдельной проверкой (`IMAGE-CHART-1`) на том же движке, с `resources={"light"}` и своими ключами порогов `image.chart.<настройка>.*`; общие ключи остаются запасными значениями.
- `Scene.prepare` только проверяет готовность (например, люксметр) и не управляет светом: в синхронной фазе её вызывают 8 процессов разом. Кто выставляет свет один раз на всех (координатор или первое место), решается на этапе 6.

### Сроки и отказы камеры

- SOAP: тайм-аут 10 с; повтор — только один, на `CameraUnreachable` через 2 с.
- Вход: на отказ (`credentials_rejected`) повторов нет.
- Нагрузка ONVIF ≈ 80 вызовов на камеру за проверку.
- RTSP: тайм-аут 10 с; одна сессия на камеру в каждый момент; ожидание ключевого кадра — `keyframe_wait_s`; выборка ≤ 32 МБ и ≤ 300 кадров.
- ffmpeg: срок 20 с на вызов (`DECODE_TIMEOUT_S`).
- Срок проверки для планировщика считается от потолков, как `check_timeout_s()` у потока: 9 настроек × 6 снимков × (12 + 10 + 5) с + 9 × 4 × 1,5 с + 120 с + 60 с ≈ 1700 с.
- Обычная длительность: ≈ 4,5 с на снимок → 5–6 минут на камеру; 8 камер идут параллельно, поэтому весь прогон тоже 5–6 минут.
- Память: ≈ 30 МБ на процесс камеры (кольцо кадров).

### Данные и секреты

- Новых секретов нет. Пароль камеры берётся из системного хранилища (`keyring`) и живёт в памяти процесса камеры. В ONVIF он уходит только дайджестом WS-Security, в RTSP — только в заголовке Authorization существующего клиента. В адрес RTSP, аргументы ffmpeg, журнал и `measure.json` он не попадает.
- Обмен SOAP (`onvif.txt`) проходит `redact` в `RunStore`. Текст отказа камеры (Fault) в причине строки обрезается до 300 символов и проходит `scrub`.
- Кадры — изображение бокса: в кадр может попасть человек у стенда. Хранятся только локально в папке прогона, наружу программа их не отправляет.
- Двоичные доказательства пишутся без вырезания секретов (так устроен `RunStore`). Для JPEG это безопасно: ffmpeg кодирует его заново из пикселей, метаданные камеры в файл не переходят. Выборка потока (`clip_*.h264`) — байты камеры как есть, в ней могут быть SEI-блоки с любым содержимым. Программа их не показывает и не разбирает, их читает только ffmpeg.

### Табу (AD-7) и ограничения записи

- `SetImagingSettings`, `GetImagingSettings`, `GetOptions` (Imaging), `GetProfiles`, `GetStreamUri` нет в `FORBIDDEN_ONVIF` (проверено по `core/taboo.py`), поэтому проверка разрешена. Запросы идут только через `SoapClient` → `http.request`: `check_onvif` проверяет имена всех элементов тела.
- При полной записи или возврате в тело попадает XML, который прислала камера. Его заново сериализует ElementTree, затем `check_onvif` проверяет все элементы. Если враждебная камера вложит, например, `SetUser` внутрь ImagingSettings, будет `TabooViolation`: запрос не уйдёт, строка получит «ошибку стенда».
- RTSP — только методы чтения (`check_rtsp`, `RTSP_READ_METHODS`). Новых сокетов и клиентов нет: `tests/test_architecture.py` должен по-прежнему проходить без исключений для `checks/image/`.
- Сверх табу у фичи свои правила, которые держит код:
  - белый список полей `ImagingWriter`;
  - неизменность блоков `Exposure`, `IrCutFilter`, `Focus` и `ImageStabilization` проверяется до отправки (`ImageWriteRefused`): режим экспозиции программа не меняет даже с галочкой;
  - запись идёт только при `ctx.allow_writes`;
  - снимок и возврат (AD-3) обязательны.
- Адреса — только со стенда: служба Imaging берётся из `service_urls` (службы на чужом хосте отбрасываются), поток — через `to_stand_address`.

### Точки входа и права

- Новых точек входа нет: программа ничего не слушает. Чтобы получать от камеры данные, она сама подключается к ней как клиент.
- Аутентификация к камере — существующая (WS-Security digest, RTSP Digest/Basic). На отказ входа повтора нет (never.md, 2026-11-05).
- Права: запись настроек изображения только с галочкой «изменяющие». Место «цветовой бокс»: в тёмной комнате проверка пропускается штатным `skip_reason`.

### Что может прислать враждебная или неисправная камера

| Ввод | Риск | Мера |
|---|---|---|
| Огромное разрешение в SDP или потоке | память и время декодера | размер выхода ffmpeg задан нашим фильтром (1280 px и фрагмент ≤ 1280 × 720); по ffprobe кадр больше 8192 × 8192 или 0 → `FrameTooLarge`, «ошибка стенда» |
| Бесконечный или очень плотный поток | диск, память | выборка ≤ 32 МБ и ≤ 300 кадров; срок `clip_s`; ffmpeg — 20 с |
| Поток, который ломает декодер | уязвимость ffmpeg | ffmpeg — отдельный процесс со сроком, вход из временного файла, без адреса и пароля в аргументах; версия ffmpeg в сборке отслеживается вручную (pip-audit её не видит) |
| Диапазон: не число, NaN, ±∞, модуль больше 10⁶, `min > max` | деление, переполнение, запись мусора | проверка до вычисления положений; запись не делается, строка «не прошла» или «пропущена» (см. «Контракты») |
| Чтение назад: мусор вместо числа | ложное «прошла» | разбор как число с теми же проверками; не число → «не прошла» (S6) |
| Токен источника видео длиннее 64 символов или с разметкой | XML-инъекция в запрос | `escape()`, как в `snapshot.py`; длиннее 64 (ReferenceToken ONVIF) → строки «пропущена» |
| Огромный ответ SOAP | память процесса камеры | общий риск: `http.request` читает тело целиком. Рекомендация для ядра — предел тела ответа (например, 4 МБ) в `http.py`; для этой фичи исходный XML ImagingSettings в журнале и снимке ограничен 64 КБ, иначе запись не начинается («ошибка стенда») |
| Текст отказа, имена профилей и источников в HTML | XSS в HTML-протоколе | автоэкранирование Jinja2; в `src` картинок — только пути из `evidence_dir`, которые создал `RunStore` через `safe_name`; путь проверяется на нахождение внутри папки прогона, `..` и абсолютные пути отбрасываются |
| Внешние ссылки в HTML для PDF | загрузка из сети при печати | в разметке нет ничего от камеры, кроме экранированного текста; `QTextDocument` с `base_dir` папки прогона подгружает только локальные файлы |

### Куда пишутся файлы

| Что | Где | Чьё имя |
|---|---|---|
| временные выборки потока | системная временная папка, `qa-image-*` (`TemporaryDirectory`); удаляются в `finally`, остатки снятого процесса — при старте прогона | программы |
| доказательства | `runs/<прогон>/evidence/<место>/<ID строки>/` | программы, через `safe_name` |
| журнал незавершённой записи | `runs/pending-image/<адрес>_<порт>.json`, атомарно с `fsync` | адрес из стенда, очищен (`journal_file`) |
| отчёт сравнения и графики | `runs/<прогон>/image_compare.*`, `runs/<прогон>/compare/*.png` | программы |

Ни одно имя файла и ни один путь не строятся из ответа камеры.

### Применимые фреймворки

- **OWASP Top 10** (отмечен в security.md):
  - A03, инъекции — XML через токены и HTML через ответы камеры: экранирование;
  - A06, уязвимые компоненты — `numpy` через pip-audit, ffmpeg — ручной учёт версии;
  - A08, целостность данных — атомарный журнал записи.
- **MITRE ATLAS — не применим.** В фиче нет ML- и LLM-компонентов: величины — детерминированные формулы над пикселями, правила — пороги из конфигурации. Если в этап войдёт VMAF (обученная модель оценки качества, см. «Решения»), применимость нужно пересмотреть. Модель там сторонняя и не обучается на наших данных, поэтому ожидаемо остаётся «не применим».
