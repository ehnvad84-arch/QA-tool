# План испытаний 06.11: камеры разных производителей

Сборка: **QA-tool 0.4.1** (`v0.4.1-trial5`, ветка `feature/stream`). Проверена 05.11: `doctor` прошёл, опубликованный AppImage прогнал 8 виртуальных камер за 132 с, 8 протоколов. Установщик Windows проверен только сборкой в CI: запуска на компьютере стенда в этой проверке не было.

Отладочная плата «Рувер» занята проектом прошивки: в испытания не входит, вход и прогоны на ней не делаем.

## Что закрываем

| Задача | Модуль | Камеры | Изменения на камере |
|---|---|---|---|
| T14 (`stream`) | Поток | все, кроме платы | нет, только чтение |
| T10 (`web`) | Просмотр веб-интерфейса | все, кроме платы | нет, один вход и выход |
| T10 (`onvif`) | Архив | только с Profile G и картой | запись по галочке, отдельное решение |
| T8 (`vendor-api`) | API «Рувер» | перенесена, см. ниже | — |

## Подготовка

1. Поставить сборку на компьютер стенда прямо в сеть камер. Через туннель UDP не доходит, и строка STREAM-NET-1 будет «пропущена».
2. На Windows разрешить программе доступ в брандмауэре, иначе проверка UDP тоже будет пропущена.
3. Записать по каждой камере: производитель, модель, прошивка, адрес, логин, пароль. Пароль сверить через веб-интерфейс камеры вручную, до запуска программы.
4. Проверить часы камеры: при расхождении с компьютером стенда вход по ONVIF может не пройти.

## Порядок на каждую камеру

Сначала одна камера каждого производителя, не восемь сразу. Неверный пароль или отказ по входу останавливает работу с этой камерой до выяснения причины, вход не повторяем.

1. **Сценарий по умолчанию:** «изменяющие», «разрушающие» и «стресс» выключены. Прогон одной камеры.
2. **Проверить вход после прогона:** тест SECURITY-1-1-1 намеренно шлёт неверные токены. Если камера заблокировала адрес, тест добавить в исключения до следующего прогона.
3. **Разобрать протокол:** каждая ложная «не прошла» заводится отдельной задачей (критерий T14).
4. **Просмотр веб-интерфейса (T10):** `~/tools/qa-web-look/look.py`, по одной камере. Отчёт — вид входа, остановленные запросы, сообщения WebSocket. Настройки до и после должны совпасть.
5. **Все камеры вместе:** один прогон на восьми местах.
6. **Стресс:** галочка «Стресс-тест», срок не меньше двух тайм-аутов сессии RTSP. Часовой стресс ещё не проверялся, запускать в конце дня.

## Поток: на что смотреть

- **H.265 на настоящем потоке:** не проверялся модулем «Поток», критерий T14.
- **UDP и Windows:** не проверялись.
- **Пороги:** значения стартовые. Камера с кадрами B реже одного на 50 может дать ложные пропуски кадров.
- **ONVIF проходит, а видео отказано при верном пароле:** снять заголовок 401 отдельно. Камера только с Digest SHA-256 получит неверную попытку: программа считает только MD5.
- **`Basic` и `Digest` в одном заголовке:** программа войдёт через Basic. Строка STREAM-AUTH-1 в этом случае может быть ложной.
- **403 на DESCRIBE:** теряются все потоки камеры, это принятый предел.

## API

- **Другие производители:** адаптеров нет. Строк API в протоколе не будет, это не ошибка. Камеры проверяются ONVIF и потоком.
- **«Рувер»:** T8 переносится. Адаптер входит по описанию API 0.5.4 (MD5), а в текущих исходниках прошивки вход PBKDF2 и HMAC. Сверить способ входа с проектом прошивки до первого прогона с `vendor: ruver`, иначе неверные попытки уйдут на камеру. Камеру «Рувер» с рабочей прошивкой пока ставить как `generic`.

## Что привезти обратно

Папки прогонов `QA-…` и отчёты `reports/*.json` из просмотра. Пароли в них не попадают, но ответы камер есть: вендорские материалы в git не копировать.
