# Спецификация: vendor-api

Статус: утверждена (Гейт 1, директор 2026-11-04: «1 утверждаю, 2 да»)
PRD: docs/ROADMAP.md, этап 3; AD-4 (адаптеры производителей), AD-3, AD-7

## Зачем — главная сессия

ONVIF не видит большую часть настроек камеры «Рувер». Нужно проверить её собственное API: каждая операция отвечает по описанию, а записанная настройка читается обратно и возвращается как была. Заодно появляется механизм адаптеров: следующие производители подключаются так же (AD-4).

## Что известно из разбора источников (2026-11-04)

- Описание `ruware-api-release-0.5.4.json` устарело: 55 адресов интерфейса камеры 0.6.14 в нём нет, 41 адрес описания интерфейс не использует.
- Основа — `www/openapi/doc/openapi.yaml` из репозитория прошивки: версия 0.6.7_p4, 203 адреса, все есть в интерфейсе камеры, в интерфейсе сверх него 12 адресов.
- Вход: `GET /api/auth/create_session`, затем `POST /api/auth/login` с паролем `MD5(пароль:идентификатор сеанса)`, дальше заголовок `X-Session-ID`. Камера держит не больше 3 сеансов, неверный пароль расходует счётчик попыток.
- Метод, `operationId` и краткое описание не определяют, изменяет ли операция настройку: есть чтение через POST, а описания бывают неверны (`/api/recorder/remove_dir` описан как «Включить запись»). Вид операции задаётся закрытыми списками в скрипте карты, записанными руками.
- Не всякий GET — чтение: `/api/auth/create_session` занимает сеанс, `/api/users/get_password` запрашивает пароль. Оба в обход не входят.
- Единая точка табу (`http.py`, `check_web_request`) сейчас не пропустит сам вход: слово `auth`. Отказывает она и `/api/image/reset_*`, и `/api/video/multicast_*`.
- Табу по описанию 0.5.4 закрывает 35 изменяющих операций из 149. Прореха: настройки NTP в API открыты, хотя в ONVIF `SetNTP` запрещён.

## Поведение (BDD) — главная сессия

### S1: Вход и сеанс

- **Дано** камера «Рувер» с верным паролем
- **Когда** начинается модуль API
- **Тогда** программа открывает один сеанс на камеру и закрывает его в конце, в том числе при сбое, остановке и подходе к пределу времени проверки
- **Когда** камера сама закрыла сеанс по времени
- **Тогда** разрешён один повторный вход: пароль уже подтверждён

### S2: Неверный пароль

- **Дано** камера не приняла пароль на CORE-CONNECT-1 или на входе в API
- **Тогда** входов больше нет, строка `API-RUVER-1` «пропущена», задач нет; всего не больше одной попытки входа в API за прогон

### S3: Нет свободного сеанса

- **Дано** на камере заняты все 3 сеанса
- **Тогда** строка `API-RUVER-1` — «ошибка стенда» с причиной «нет свободного сеанса», задач нет

### S4: Чтение всех настроек

- **Дано** изменяющие проверки выключены
- **Когда** идёт модуль API
- **Тогда** каждая операция вида «чтение» вызвана один раз; ответ 200 и совпадение со схемой описания — «прошла», иначе «не прошла» с запросом и ответом в доказательствах
- Операция с обязательными параметрами без значения в карте — «пропущена: нужны параметры»; 401 и 403 при живом сеансе, тайм-аут — «ошибка стенда»; двоичный ответ — в доказательствах только размер и хеш

### S5: Операция, которой нет в этой прошивке

- **Дано** операция есть в описании, но камера отвечает 404
- **Тогда** «пропущена» с причиной «нет в прошивке <версия>», а не задача программистам

### S6: Записал — прочитал — вернул

- **Дано** разрешены изменяющие проверки
- **Когда** проверка меняет настройку на другое допустимое значение
- **Тогда** чтение возвращает новое значение, затем исходное значение возвращается и сверяется. Несовпадение — «не прошла»; значение не вернулось — «не прошла» с причиной «камера осталась изменённой»
- Вид «запись» — только операция с чтением на том же адресе и значением, которое можно вернуть. Настройка, требующая перезагрузки по ответу `/api/service/need_reboot`, не пишется вовсе: строка «пропущена: применяется после перезагрузки»
- Перед записью и после неё — полный обход чтения; настройка из вида «запись», которая разошлась, возвращается ещё раз; оставшаяся разница по полям, кроме живых (время, счётчики), — «камера осталась изменённой»
- Надпись, сдвинутая записью, возвращается операцией `/api/osd/set_block_position` (вид «только возврат») по снимку «до»; сам сдвиг остаётся строкой «не прошла»
- Сверка видит только основной поток и дневной профиль: запись идёт только туда, побочные изменения на других потоках и в ночном профиле не видны (известное ограничение)
- Подход к пределу времени или остановка: новые значения не пишутся, текущее возвращается и сверяется до выхода

### S7: Недопустимое значение

- **Дано** разрешены изменяющие проверки и описание задаёт пределы
- **Когда** отправлено значение вне пределов
- **Тогда** камера отвечает ошибкой, значение не меняется; принятое значение — «не прошла», настройка возвращается

### S8: Табу

- **Дано** операция меняет сеть, учётные записи, NTP, сброс или импорт настроек
- **Тогда** она не отправляется никогда, ни с какой галочкой; в протоколе «пропущена: запрещено табу»

### S9: Разрушающие операции

- **Дано** перезагрузка, форматирование и подготовка карты, удаление записей
- **Тогда** без галочки «разрушающие» не отправляются: «пропущена: не разрешено сценарием»
- Операции без обратного хода (сброс параметров, события, туры, пресеты, движение и калибровка PTZ, синхронизация GPS) — вид «не вызывается» с причиной в таблице карты

### S10: Вид в окне и протоколе

- **Дано** модуль закончился
- **Тогда** в ходе проверки одна строка «API „Рувер“: N операций», в протоколе строка на каждую операцию, в задачах — только «не прошла»

### S11: Камера другого производителя

- **Дано** камера без адаптера
- **Тогда** строк API нет, общий слой работает как раньше (AD-4)

### S12: Функции, которых нет у модели (T8, живая камера)

- **Дано** `/api/hardware` сообщает, что функции у модели нет (LTE, ГЛОНАСС, HTTPS, SD-карта, запись, датчик удара, диафрагма)
- **Тогда** её операции не вызываются: «пропущена: нет у этой модели», задач нет

### S13: Экспорт настроек (T8, живая камера)

- **Дано** экспорт настроек на прошивке 0.6.14 перезапускает службу API
- **Тогда** экспорт идёт после сверки настроек; обрыв после него — «не прошла» на строке экспорта, а не ошибки стенда на соседних строках

## Вне рамок — главная сессия

- Проверка эффекта настройки на картинке (этап 7) и поток (этап 4).
- Адаптеры других производителей: только механизм.
- `/api/recorder` как замена архива ONVIF: чтение — да, проигрывание — нет.

## UI — главная сессия

Новых экранов нет. Модуль «API» появляется на «Сценарии» одной строкой «API «Рувер»»; для камер без адаптера она неактивна, как проверки чужого производителя.

## Архитектура, API и данные — главная сессия

- `scripts/gen_api_map.py` — разбирает `~/projects/hisi-fw-dev-gstack/www/openapi/doc/openapi.yaml` и пишет `src/qa_tool/data/ruver_api_map.json`: адрес, метод, вид (чтение, запись, табу, разрушающая, не вызывается), параметры, пределы, схема ответа. Без `description` и `example`: в репозиторий идёт наша карта, а не файл прошивки (never.md). Закрытые списки вида и причины — в скрипте, руками.
- `drivers/camera/ruver/client.py` — `RuverClient`: вызовы только через `drivers/camera/http.request` (табу, AD-7). Контекстный менеджер закрывает сеанс при любом исходе. Адрес вне карты и изменяющая операция без разрешения — отказ до `http.request`.
- `checks/api/ruver.py` — **одна составная проверка на камеру** `API-RUVER-1`: один контекст сеанса, строки через `ChildResult`, как `checks/onvif/onvif_tt.py`. Отдельные проверки на раздел не годятся: снятие процесса планировщиком пропустило бы `finally`, сеанс и исходное значение пропали бы. Свой предел времени меньше `timeout_s`: планировщик не снимает процесс посреди записи; `timeout_s` считается по размеру карты.
- `core/taboo.py`: закрыть NTP и источник времени, `/api/datetime` целиком. **Единственное исключение из слов-признаков** — точный список `/api/auth/create_session`, `/api/auth/login`, `/api/auth/logout`; всё остальное в `check_web_request` не ослабляется, это закрепляет тест. `/api/video/multicast_*` — вид «табу» (сеть), `/api/image/reset_*` — «не вызывается». Правка единой точки — только после ответа директора, не в автоитерации.
- Проверка схем — `jsonschema` (в `pyproject.toml` и `uv.lock`). schemathesis не берём: он сам шлёт запросы мимо `http.py` (AD-7); AGENTS.md и AD-4 обновляются вместе с T7.
- Адаптер выбирается полем `Camera.vendor`; `CheckSpec.vendors` уже отсекает чужие камеры (`core/checks.py:152`).

## Безопасность — главная сессия

- Пароль только как MD5 с сеансом; идентификатор сеанса вырезается из доказательств (`X-Session-ID` добавить в `redact`).
- Ответы `/api/configuration`, `/api/users/*` могут содержать секреты: в доказательства — только после `redact`; `/api/service/export_settings` и `/api/service/log` — только размер и хеш; снимок настроек — в памяти.
- Новая зависимость `jsonschema` — через pip-audit в CI.
- Угроза: новая прошивка с новым опасным адресом. Защита — операция не из карты не вызывается вовсе.

## Решения — главная сессия

| Вопрос | Выбрано | Почему | Отвергнуто |
|---|---|---|---|
| Источник описания | `openapi.yaml` 0.6.7_p4, карта генерируется | ближе всего к 0.6.14 | `ruware-api-release-0.5.4.json`: 55 адресов нет |
| Обход API | свой, через `http.py` | табу не обойти | schemathesis: шлёт запросы сам |
| Неописанные операции | не вызываются | неизвестный адрес может быть опасным | вызывать всё из интерфейса |
