# Спецификация: ruver-login

Статус: утверждена (директор 2026-11-21: «разрешаю challenge в AD-7»)
PRD: docs/PRD.md → адаптер API «Рувер» (этап 3)

## Зачем — главная сессия

Задача из списка от 04.11: «Перед T8 этапа 3 сверить вход API „Рувер“ с прошивкой». Разбор исходников прошивки (~/projects/hisi-fw-dev-gstack, 20.11) показал: у прошивки своей сборки два сервера. SSC (полное приложение, сейчас на платах) принимает и MD5, и новый вход PBKDF2; лёгкая `rw-camd` принимает только PBKDF2 и каждый наш MD5-вход считает неудачей — 5 неудач закрывают адрес стенда на 5 минут, в том числе для ONVIF. Заводская прошивка (0.6.14) знает только MD5. Программа должна входить в любую из них одной попыткой.

## Поведение (BDD) — главная сессия

### S1: камера своей сборки (SSC или rw-camd)
- **Дано** камера отвечает на `POST /api/auth/challenge` солью, числом итераций и `pbkdf2-sha256`
- **Когда** проверка API входит в камеру
- **Тогда** пароль уходит как HMAC-SHA256 сеанса ключом PBKDF2, попытка входа одна, в открытом виде пароль не уходит

### S2: заводская камера
- **Дано** камера на вызов отвечает чем угодно, кроме полного правильного ответа (404, 405, HTML, другие поля)
- **Тогда** вход MD5, как раньше, одной попыткой

### S3: неверный пароль
- **Тогда** одна попытка, отказ не повторяется ни при каком входе

### S4: блокировка сторожем попыток (429)
- **Тогда** «камера заблокировала вход», повторного входа нет даже после ожидаемого перезапуска службы

### S5: чужой ответ с огромным числом итераций
- **Тогда** вход не начинается (попытка не тратится), причина в протоколе

### S6: повторный вход после истечения сеанса
- **Тогда** вызов не повторяется: способ входа запомнен на клиента

## Вне рамок — главная сессия

- Вход браузера в веб-интерфейс (свои окна входа AD-7) не меняется.
- Определение типа прошивки по версии — не нужно: вызов отвечает однозначно.

## Архитектура, API и данные — backend-architect

`drivers/camera/ruver/client.py`: `parse_challenge` (строгий разбор), `challenge_password`, `_ask_challenge` (один раз на клиента), 429 как блокировка, `login_method` для доказательства. `core/taboo.py`: в `CAMERA_LOGIN_REQUESTS` добавлен `POST /api/auth/challenge` (точное совпадение адреса). Mock: `login_mode` md5/both/challenge, `challenge_answer`, `lockout_429`.

## Безопасность — backend-architect

Новый адрес в исключениях табу — только буквально, без параметров и хвостов (`;/../`, %XX — тест). Вызов ничего на камере не меняет (rw-camd `Auth.cpp:158` только читает; SSC считает соль из имени, `LoginChallenge.cpp:51-58`) и попыткой не считается. Пароль уходит только как HMAC; предел 1 000 000 итераций защищает рабочий процесс от чужого ответа.
