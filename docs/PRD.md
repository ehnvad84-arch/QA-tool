# PRD: QA-tool — стенд проверки IP-камер

## Проблема и для кого

IP-камеры — свои и любых других производителей — проверяются вручную и выборочно: ONVIF — сторонними утилитами, веб и API — «на глаз», картинка и аналитика — субъективно. Ошибки прошивки доходят до заказчика: например, камера с одним Profile S показывает картинку в любом регистраторе, но архив с SD-карты по ONVIF не отдаёт. Сравнить камеры разных производителей в одинаковых условиях нечем.

**Инструмент — для любых IP-камер** (решение директора 2026-11-03): не заточен под одного производителя; камера без отдельной поддержки проверяется полностью по общим протоколам (AD-4).

Пользователи:
- **ОТК, инженер стенда, отдел закупок и испытательная лаборатория** — запускают прогон, получают протокол по каждой камере любого производителя.
- **Программисты прошивки** — получают таблицу задач с шагами воспроизведения и доказательствами.
- **Руководство и продажи** — сравнение своих камер с конкурентами и между версиями прошивки.

## Цели и метрики успеха

- Один прогон проверяет до 8 камер одновременно без участия человека (кроме установки камер на стенд).
- Протокол по каждой камере: все модули из списка ниже, итог «прошла / не прошла» по каждой проверке с доказательством.
- Каждая ошибка → строка задачи программистам, которую можно воспроизвести по описанию.
- Ложных «не прошла» на эталонной камере — 0 при трёх повторных прогонах подряд.
- Специально внесённая ошибка (отключённая настройка, сломанный архив) находится в 100 % случаев.
- Программа и протоколы одинаково работают на Windows и Linux.

## Требования

### Функциональные

1. **ONVIF** — все операции профилей S, G, M, T из официальных спецификаций; матрица «обязательно для профиля → поддержано → работает»; реальное проигрывание архива по Profile G; метаданные аналитики по Profile M.
2. **API производителя** — если для камеры есть адаптер (первый — «Рувер», OpenAPI): каждая операция — ответ по схеме, ошибки на неверный ввод, «записал → прочитал то же».
3. **Веб-интерфейс любой камеры** — универсальный обход: каждая кнопка, переключатель и поле на каждой странице — отработала или нет, ушёл ли запрос и какой ответ, ошибки страницы, время отклика; где можно — изменилось ли значение на камере (через ONVIF или API адаптера).
4. **Интерфейсы камеры** — тревожные входы и выходы, микрофон, динамик (и прочие из паспорта модели).
5. **Объектив** — зум, фокус, автофокус, повторяемость пресетов; работа ИК-фильтра.
6. **День/ночь и ИК-подсветка** — время и корректность переходов, отсутствие дребезга, работа подсветки в темноте.
7. **Поток** — стабильность, стресс-тест максимальной нагрузки, потеря пакетов, джиттер, пропуски кадров; длительный прогон.
8. **SD-карта** — запись, поиск, выдача архива по API и ONVIF, непрерывность записи.
9. **Картинка** — для каждой настройки изображения снимки «до/после» и заключение: эффект есть, его нет или он обратный.
10. **Кодеки** — соответствие заданным параметрам и качество на единицу битрейта.
11. **Аналитика и детекторы** — срабатывание на сцены стенда, задержка, ложные срабатывания.
12. **Сравнение камер** — сводная матрица и замечания по всем камерам прогона.
13. **Протокол** — PDF, Excel, HTML по каждой камере с таблицей задач программистам; отчёт сравнения.
14. **Интерфейс** — подсказка при удержании мыши 1 секунду на любом элементе; F1 — справка по текущему экрану; руководство пользователя и руководство по сборке стенда.
15. *По желанию, последним этапом* — защищённость прошивки (EMBA, сетевой скан).

### Нефункциональные

- До 8 камер в одной сети одновременно; планировщик не допускает взаимного влияния проверок.
- Камера после прогона остаётся с исходными настройками (кроме разрешённых галочкой разрушающих проверок).
- **Табу:** сетевые настройки, логины и пароли камеры программа не меняет никогда — включая сброс к заводским и импорт конфигурации (AD-7).
- Прогон переживает потерю связи с камерой и перезагрузку: камера помечается, остальные продолжают.
- Прогон можно запустить без окна, из командной строки (ночные прогоны).
- Windows 10/11 и Ubuntu 22.04/24.04; установщик ставит всё нужное (ffmpeg, браузер для веб-проверок).
- Язык интерфейса, справки и протоколов — русский.

## Вне рамок

- Собственное API производителя без адаптера — для такой камеры работает общий слой (AD-4).
- Выгрузка задач во внешние трекеры (AD-5).
- Проверки смены сетевых настроек, учётных записей и сброса к заводским — табу (AD-7); сеть и учётные записи проверяются только чтением.
- Официальная сертификация ONVIF — инструмент даёт сигнал для разработки, не Declaration of Conformance.
- Проверка качества сборки «железа» по AQL — это ОТК производства, не программа (может использовать её протоколы).

## Ключевые решения и ограничения

См. docs/rules/architecture.md (AD-1 … AD-6). Кратко: Python + PySide6, одна программа и две сборки; фазы прогона и блокировки оборудования; восстановление настроек; объём проверок по производителю; задачи только в протоколе; onvif-tt как зависимость.

Стенд — покупное оборудование под управлением программы (docs/stand/equipment.md).

## Ответы директора (2026-11-03)

1. **Камеры:** любые IP-камеры — «Рувер», Dahua, Hikvision, Axis, Uniview, Raysharp и другие; живые камеры для подключения есть. Все идут через общий слой; собственное API — через адаптер производителя (AD-4).
2. **Компьютер стенда:** обе ОС на равных — Windows и Ubuntu. CI собирает и тестирует обе сборки с этапа 1; EMBA (этап 10) — только в Linux-сборке.
3. **Место:** есть и цветовой бокс, и тёмная комната. В программе два «места стенда»: бокс — картинка, цвет, кодеки, аналитика; тёмная комната — ночь, ИК-подсветка, день/ночь. Сценарий прогона знает, где стоит камера, и предлагает только доступные проверки.
4. **Форма протокола:** своей формы у ОТК нет — проектируем свою (этап 1).
5. **Пороги:** подбираем сами — стартовые значения в конфигурации, уточняются по прогонам на эталонных камерах; каждое значение порога и его происхождение печатаются в протоколе.

## Риски

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Ложные «не прошла» по картинке из-за нестабильного света | средняя | высокое | калибровка стенда по эталонной камере, самопроверка света перед прогоном |
| Веб-интерфейс меняется с каждой прошивкой — проверки кнопок ломаются | высокая | среднее | карта кнопок строится автоматически из исходников `www/` и обхода страниц, а не вручную |
| Одна сеть 1 Гбит/с не тянет стресс-тест 8 камер | средняя | среднее | порт 2,5/10 Гбит/с к компьютеру стенда; замер полосы в самопроверке |
| onvif-tt перестанут развивать | низкая | среднее | закреплённая версия; MIT — можно продолжить своими силами |
| Изменяющая проверка «испортит» камеру | низкая | высокое | AD-3: снимок и восстановление настроек, разрушающие — только по галочке |
