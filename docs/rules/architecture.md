## AD-1: Одна программа на Python + PySide6, две сборки — Windows и Linux

- Контекст: нужны «две приложки» под Windows и Linux.
- Решение: один код, интерфейс на Qt (PySide6), установщики PyInstaller + Inno Setup и AppImage/.deb.
- Почему: onvif-tt, Playwright, OpenCV, ffmpeg — всё есть на Python под обе ОС; одно исправление сразу в обеих сборках.
- Цена: размер установщика (Qt + ffmpeg + браузер Playwright); EMBA работает только на Linux.
- Дата: 2026-11-03

## AD-2: Прогон делится на фазы, общее оборудование — через блокировки

- Контекст: до 8 камер одновременно, а свет, экран, динамик и микрофон стенда общие.
- Решение: фазы «сетевая (параллельно) → синхронная стенда (все камеры разом) → поочерёдная → стресс»; каждая камера — отдельный процесс; планировщик выдаёт ресурсы стенда по блокировкам.
- Почему: проверки не мешают друг другу, а одна смена условий снимается всеми камерами — честное сравнение.
- Цена: прогон длиннее, чем при полном параллелизме.
- Дата: 2026-11-03

## AD-3: Изменяющие проверки сохраняют и восстанавливают настройки; разрушающие — только по галочке

- Контекст: проверки меняют настройки камер; камера после стенда должна остаться как была.
- Решение: перед изменением — снимок конфигурации (API `/api/configuration` или ONVIF Get*), после — восстановление и сверка; сеть и учётные записи не восстанавливаются, потому что не меняются (AD-7). Обновление прошивки и форматирование SD — только по явной галочке в сценарии.
- Почему: камера не уходит со стенда испорченной; повторный прогон даёт тот же результат.
- Цена: каждая изменяющая проверка дольше на чтение и восстановление.
- Дата: 2026-11-03

## AD-4: Инструмент для любых IP-камер: общий слой + адаптеры производителей

- Контекст: директор 2026-11-03 — «тест-тул не для камер Рувер, а для любых IP-камер; не затачивай проект под Рувер». Прежняя редакция («Рувер» — всё, конкуренты — только ONVIF) отменена.
- Решение:
  - **Общий слой — для любой камеры без доработок:** ONVIF (все профили), RTSP-поток и кодеки, картинка, день/ночь и ИК-фильтр (ONVIF Imaging), тревожные входы/выходы (ONVIF DeviceIO и Events), звук, SD-карта и архив (Profile G), аналитика (ONVIF Events, метаданные Profile M), веб-интерфейс — универсальный обход браузером (кнопки, поля, запросы, ошибки, время отклика), сетевой скан защищённости.
  - **Адаптер производителя — по желанию**, плагин в `drivers/camera/<vendor>/`: собственное HTTP API (описание OpenAPI или своя карта команд), подсказки для веб-обхода, список запрещённых команд этого API (AD-7). «Рувер» — первый адаптер (`openapi.yaml` 0.6.7_p4), дальше — Hikvision ISAPI, Dahua CGI, Axis VAPIX, Uniview LAPI и др. по мере надобности.
  - Камера без адаптера проверяется общим слоем полностью; адаптер только добавляет проверки.
- Почему: сравнивать камеры разных производителей можно только одинаковыми проверками; ONVIF и браузер есть у всех.
- Цена: эффект кнопки веб-интерфейса чужой камеры подтверждаем через ONVIF (прочитать то же значение) или по ответу сервера — глубже, чем без адаптера, не заглянуть.
- Дата: 2026-11-03

## AD-5: Задачи программистам — только в протоколе

- Контекст: куда отдавать найденные ошибки (решение директора 2026-11-03).
- Решение: таблица задач в протоколе (PDF и Excel): заголовок, модуль, важность, шаги воспроизведения, ожидалось/получено, доказательство. Внешние трекеры не подключаем.
- Почему: протокол — единый документ ОТК, раздаётся вручную.
- Цена: задачи переносятся в трекер руками.
- Дата: 2026-11-03

## AD-6: ONVIF — onvif-tt как зависимость, свои проверки рядом

- Контекст: onvif-tt (MIT) уже имеет 148 проверок, но без Profile M и без проигрывания архива G.
- Решение: подключить onvif-tt пакетом с закреплённой версией, его результаты переводить в наш формат; недостающие проверки писать в `checks/onvif/` нашего проекта. Каталог покрытия — из onvif/testspecs.
- Почему: не дублировать готовое, а обновления onvif-tt получать заменой версии.
- Цена: зависим от их формата результатов; при обновлении — проверка совместимости.
- Дата: 2026-11-03

## AD-7: Табу — сеть, логины и пароли камеры не меняются никогда

- Контекст: директор запретил менять у камер сетевые настройки, логины и пароли (2026-11-03). Ошибка здесь выбивает камеру из сети стенда или запирает её.
- Решение: список запрещённых команд в `core/taboo.py` — ONVIF (Set* сети, SetNTP, Hostname, IP-фильтр, Discovery, 802.1X, AccessPolicy, Create/Delete/SetUser, SetSystemFactoryDefault, RestoreSystem, StartSystemRestore) и изменения API «Рувер» по `/api/network`, `/api/users`, `/api/snmp`, `/api/lte`, `/api/datetime` (NTP и источник времени), `/api/video/multicast_*`, `/api/service/reset`, `/api/service/import_settings`. Из слов-признаков исключены только три адреса входа в API «Рувер» (`GET /api/auth/create_session`, `POST /api/auth/login`, `POST /api/auth/logout`), точным совпадением адреса: иначе программа не войдёт в камеру. Единственный выход HTTP к камере — `drivers/camera/http.py`: путь, операции ONVIF и слова-признаки проверяются до отправки; сокеты — только `probe.py` (порты на чтение), `discovery.py` и `rtsp.py` (видео и архив; методы только из `RTSP_READ_METHODS`, проверка `check_rtsp`); `taboo_proxy.py` — посредник для onvif-tt: слушает только 127.0.0.1 и пересылает каждый запрос к камере через `http.py`; обход ловит `tests/test_architecture.py`. Нарушение — `TabooViolation`, запрос не уходит, проверка получает «ошибка стенда». Клиенты этапов 2–4 (zeep для onvif-tt, адаптеры API) подключаются только через эту точку; у браузера этапа 5 свой выход под теми же проверками (см. ниже). Галочка сценария табу не снимает.
- Веб-обход любой камеры (AD-4): браузер перехватывает каждый изменяющий запрос (POST/PUT/PATCH/DELETE) и не пропускает его, если адрес, имя поля или страница относятся к сети, учётным записям, паролям, безопасности, сбросу, восстановлению или импорту настроек (`check_web_request`); кнопки и поля на таких страницах не нажимаются вовсе. Для камеры без адаптера это единственная защита, поэтому список слов-признаков широкий: лучше не нажать лишнего.
- Браузер (дополнено 2026-11-05, утвердил директор): второй выход к камере — `drivers/camera/browser.py`, единственный модуль с `playwright`. Он работает вместо `http.py`, но под теми же проверками `core/taboo.py`; перехват стоит на всём контексте браузера и на WebSocket; запрос на адрес не из списка стенда не отправляется.
- Вход через браузер (дополнено 2026-11-05, утвердил директор): для камеры без адаптера одно окно входа за обход. Его открывает программа перед своим нажатием кнопки входа, до начала обхода, когда на странице одно поле пароля и нет признаков смены пароля. Внутри окна снимаются только слова входа и только в именах, до 4 изменяющих запросов; признаки смены пароля, опасные действия, `check_http` и `check_onvif` действуют. После отказа камеры вход не повторяется ни одной проверкой прогона. Если первый вход принят, а незавершённая запись потеряла сессию, разрешён один вход только для возврата значения. Окно выхода — одно нажатие в конце обхода по точной подписи («Выйти», «Выход из системы», logout, sign out, log out), до 2 запросов, те же запреты. `CAMERA_LOGIN_REQUESTS` остаётся точным списком для `http.py`.
- Опасные действия через браузер (2026-11-05): перезагрузка, выключение, форматирование, удаление и очистка не выполняются ни при каких галочках: элемент не нажимается, запрос не уходит. Список действует только на браузер; проверки SD по галочке «разрушающие» идут через `http.py` и его не касаются.
- Запись через браузер (2026-11-05): изменяющий запрос уходит только в окне записи, при галочке «изменяющие», с журналом и возвратом значения. Остальное останавливается и записывается в протокол.
- Почему: правило в коде, а не только в документе: случайная проверка, onvif-tt или будущий модуль не смогут его обойти.
- Цена: не проверяем смену IP, учётных записей и сброс к заводским; соответствующие тесты ONVIF (IPCONFIG-*, USER-*) исключаются на этапе 2, а их «читающие» варианты остаются.
- Дополнение 2026-11-11 (решение директора): браузер пропускает два чтения страниц входа, без которых живые камеры не дают войти, — `GET /api/auth/create_session` («Рувер», слово «create») и `GET /SDK/activateStatus` (Hikvision, слово «activate»); адрес буквально, параметры только числовые (`WEB_APPROVED_READS` в `core/taboo.py`). `http.py` это исключение не применяет.
- Дата: 2026-11-03; дополнено 2026-11-04 (утвердил директор): `rtsp.py` и `taboo_proxy.py`; 2026-11-11: чтения страниц входа в браузере; NTP, источник времени и адреса входа API «Рувер»; дополнено 2026-11-05 (утвердил директор): браузер, вход и выход через браузер, опасные действия
