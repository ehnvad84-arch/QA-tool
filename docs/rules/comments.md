Комментарий объясняет решения, ограничения и контекст, которые нельзя понять из кода. Сначала код делается понятным именами, структурой и разделением ответственности; комментарий добавляется только там, где он добавляет ценность. Имена объясняют «что», структура — «как», комментарии — «почему».

## Общие правила

- Все комментарии, docstring и `TODO` — **на русском языке**, коротко, полными предложениями, в едином стиле.
- Комментарий объясняет **почему**, а не пересказывает код: `# увеличиваем счётчик` перед `i += 1` не нужен.
- Комментарий обновляется вместе с кодом: устаревший комментарий хуже отсутствующего.
- Закомментированного кода нет — историю хранит Git.
- `TODO` и `FIXME` — только с понятным описанием (что сделать и почему) и, если есть, ссылкой на задачу: `# TODO: повторить запрос после переподключения; задача QA-12`.
- Без избыточных деталей, эмоций, споров и личных замечаний: комментарий — часть технической документации.

## Модули, классы, функции (docstring)

- Модуль: назначение, основные сценарии, важные ограничения и зависимости (потоки, тайминги, оборудование, совместимость с прошивками) — обязательно для сложных и ключевых модулей.
- Класс: роль в системе, правила использования, инварианты («`start()` до `capture()`»), потокобезопасность, работа с внешними ресурсами (сеть, файлы, оборудование).
- Функция: назначение одной фразой; параметры с единицами и допустимыми значениями (`Args:`), результат (`Returns:`), исключения (`Raises:`), предусловия, побочные эффекты (сеть, запись, блокировка ресурса), неочевидные ограничения (тайминги, особенности моделей камер). Стиль — docstring Python в формате Google, по-русски.
- Простым геттерам и очевидным методам хватает понятного имени или одной фразы.
- **Обязательно** документируются публичное API ядра (`core/`), драйверы (`drivers/`), проверки (`checks/`), протоколы (`report/`) и сложные алгоритмы — это проверяет ruff (D1).

## Комментарии внутри кода

- Нужны в неочевидных местах: обход ошибки прошивки, драйвера, библиотеки или стороннего сервиса; «магические» константы из спецификации, измерений или опыта; причина нестандартного решения; важный порядок операций; ссылка на баг, задачу, документацию протокола или поставщика.
- Каждый обход ошибки, нестандартное решение и магическая константа — с причиной и, если применимо, ссылкой на задачу или источник:

```python
# Некоторым камерам нужна пауза 250 мс после смены разрешения,
# иначе RTSP-сессия завершается ошибкой 454. Подробности: задача QA-1423.
time.sleep(0.25)
```

- Основной комментарий — **над** блоком с тем же отступом; короткая пометка справа — только если помещается и не мешает чтению.

## Чего избегать

| Неправильно | Правильно |
|---|---|
| `# i += 1` | комментарий не нужен |
| `# обработка ошибки` перед очевидным `try` | объяснить, почему ошибка обрабатывается именно так |
| закомментированный старый вариант функции | удалить: история в Git |
| `# TODO: потом исправить` | `# TODO: обработать тайм-аут переподключения; задача QA-15` |
| комментарий, противоречащий коду | обновить или удалить |
| простыня с пересказом алгоритма | разбить функцию, дать понятные имена, оставить важные пояснения |
| английский комментарий | по-русски |

## Проверка

Комментарии ревьюятся так же, как код: точность, актуальность, польза. Перед каждым push — `.githooks/pre-push` (ruff с ERA001 и D1, `scripts/check_comments.py`, тесты) и просмотр комментариев в диффе главной сессией.
