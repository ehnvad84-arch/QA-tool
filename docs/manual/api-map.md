# API камеры: карта и сверка с ONVIF

Проверка «API камеры: карта и сверка с ONVIF» читает собственный (родной) API камеры, составляет его карту и сверяет с ONVIF. Она идёт у всех камер в сетевой фазе, после обхода веб-интерфейса и проверки API «Рувер».

**Родной API** — интерфейс производителя, через который работает веб-интерфейс камеры: у Hikvision — ISAPI, у Dahua — CGI, у «Рувер» — API по карте программы. **ONVIF** — общий стандарт, через него камеру видят регистраторы. Одна и та же настройка (яркость, режим экспозиции, битрейт) есть в обоих. Если камера сообщает её по-разному, регистратор по ONVIF видит не то, что показывает веб-интерфейс, — это задача программистам.

Что делает проверка:

- Читает родной API только запросами чтения. Запросы перезагрузки, сброса, обновления, выгрузки настроек и записи не уходят никогда.
- Входит тем же логином и паролем, что ONVIF, одна попытка на камеру за прогон. Если камера уже отвергла пароль (видео, веб-интерфейс, API «Рувер»), родной API не пробуется — «ошибка стенда». Пароль по открытому HTTP (Basic) не отправляется — строка «пропущена».
- Значения сети, учётных записей и безопасности не читаются и не сохраняются — только их описание. Пароли, ключи и токены из ответов вырезаются.
- Составляет карту: разделы, параметры, допустимые и текущие значения.
- Сверяет с ONVIF каждую настройку, для которой известна пара «настройка ONVIF ↔ параметр родного API».
- С галочкой «изменяющие» ищет пары сама (автопоиск), меняя настройки изображения и кодировщика по ONVIF и возвращая их.

Время — обычно 1–3 минуты на камеру без галочки и 3–6 минут с автопоиском.

Что в протоколе: строка «Карта родного API» (API-MAP-1), строки сверки «… значение» (API-MATCH) и «… диапазон» (API-RANGE), с галочкой — «Автопоиск соответствий» (API-SEARCH-1) и «Возврат после автопоиска» (API-RESTORE-1). Подробности — в приложении протокола «API камеры: карта и сверка с ONVIF». Полная карта — в отдельном документе «Карта API» на экране «Протоколы».

## Откуда берётся карта

- **Самоописание API.** Hikvision, Dahua и «Рувер» сами сообщают, какие у них разделы и какие значения допустимы. Программа читает их по списку своего сборщика.
- **Трафик веб-обхода.** Для камер, родной API которых программа не умеет читать напрямую (Tiandy, Beward, другие производители), карта строится из запросов, которые страница веб-интерфейса сама сделала при обходе. Своих запросов к камере программа при этом не делает. Отметьте в сценарии и «API камеры», и «Веб-интерфейс», иначе строка «пропущена: родной API не найден — нет сборщика для бренда и трафика веб-обхода». Допустимые значения в трафике не видны, поэтому по такой карте нет ни сверки, ни автопоиска.

Производитель определяется по паспорту ONVIF камеры, а если паспорт пуст или незнаком — по полю «Производитель» на экране «Камеры». Если они расходятся, сводка приложения просит проверить производителя.

Как читать сводку приложения: «разделов N; не ответили — M» — сколько разделов прочитано и сколько запросов камера отвергла (404 — раздела нет у этой модели, 403 — нет прав). Это не ошибка камеры: список разделов у сборщика общий для многих моделей.

## Пары и сверка

**Пара** — «настройка ONVIF ↔ параметр родного API» и правило перевода шкалы. У каждой настройки ONVIF свой номер `n` в каталоге программы (1 — яркость, 12 — режим экспозиции, 15 — битрейт), одинаковый у всех камер.

Шкала:

- «1:1» — значения совпадают;
- «× 0,39 + 0» — родной API считает в другой шкале (например, 0…255 против 0…100);
- «по диапазонам» — шкала строится из объявленных диапазонов обеих сторон;
- «список: AUTO ↔ auto» — перечисление.

Итоги строк:

- **«… значение» прошла** — ONVIF и родной API показывают одно и то же с учётом шкалы и допуска `api.compare_tol_pct`.
- **«… значение» не прошла** — показывают разное: одно из двух неверно. Какой режим на самом деле, видно в веб-интерфейсе. Задача программистам, серьёзная.
- **«… диапазон» не прошла** — объявленные диапазоны не совпадают (мелкая) или камера объявляет больше, чем держит на деле (серьёзная; пример — Dahua: объявлено 512…5632 кбит/с, а при H.264 держит не больше 1792).
- **пропущена** — пару не сверить на этой камере: параметра нет в карте, значение не число, оно меняется само.

«Откуда пара»: «подтверждено вручную (таблица программы)», «подтверждено вручную: кто, дата, камера» (файл `confirmed.json`), «найдено автоматически, прогон …» (библиотека), «найдено в этом прогоне», «найдено на прошивке …» — пара с другой прошивки той же модели; если по ней «не прошла», проверьте пару на этой прошивке.

## Автопоиск соответствий

Идёт только с галочкой «изменяющие». Для каждой настройки изображения из каталога, а затем для битрейта и кодека программа:

1. дважды снимает карту родного API без записи — так видно, какие параметры меняются сами;
2. записывает по ONVIF значение на 20 % или 80 % диапазона (дальше от текущего), снимает карту и смотрит, что сдвинулось;
3. записывает второе значение и снова смотрит;
4. возвращает настройку по ONVIF и сверяет всю карту с исходной.

Пара найдена, если после второй записи сдвинулся ровно один родной параметр, тот же, что после первой, и его значения ложатся на шкалу ONVIF. Копии одного параметра по профилям и потокам (у Dahua — день, ночь, обычный) считаются одним параметром. Пары, уже известные по таблице программы и библиотеке, заново не ищутся.

**Побочный эффект** — запись одной настройки ONVIF сдвинула больше родных параметров, чем листов ONVIF в записи, или параметр вне своего раздела, или другие настройки ONVIF (пример — Hikvision: запись яркости сбросила наибольшее усиление). Тогда поиск на камере останавливается, всё возвращается, а строка «Автопоиск соответствий» — «не прошла», мелкая: камера ведёт себя не так, как обещает ONVIF.

Битрейт: если камера держит меньше середины объявленного диапазона, первая запись берётся ниже того, что она держит на деле; строка «диапазон» покажет, сколько камера держит.

## Библиотека соответствий

Найденные пары и карты копятся в библиотеке рядом с папками прогонов: `<папка прогонов>/api-library/<производитель>/<модель>/<прошивка>/`. Точный путь — в сводке приложения «API камеры», строка «Библиотека». К именам папок программа добавляет короткую метку, чтобы любое имя модели было безопасным именем папки.

В папке прошивки:

- `map-<прогон>-<место>.json` и `pairs-<прогон>-<место>.json` — карта и найденные пары каждого прогона;
- `confirmed.json` — пары, подтверждённые человеком. Их программа ставит выше всех найденных.

Как подтвердить или исправить пару:

1. Найдите строку в приложении протокола (п. 3 «Сверка») или в документе «Карта API» и скопируйте путь родного параметра.
2. Откройте или создайте `confirmed.json` в папке прошивки и допишите пару:

```json
{
 "формат": "qa-tool/api-pairs",
 "версия": 1,
 "камера": {"производитель": "Hikvision", "модель": "DS-2CD2143G2-I", "прошивка": "V5.7.3"},
 "пары": [
  {
   "n": 12,
   "onvif": "Imaging/Exposure/Mode",
   "родной": "Image/channels/1/Exposure/ExposureType",
   "шкала": {"вид": "перечисление", "значения": {"AUTO": "auto", "MANUAL": "manual"}},
   "точки": [],
   "состояние": "подтверждена вручную",
   "источник": "подтверждено вручную: Иванов, 10.11.2026, камера .111"
  }
 ]
}
```

3. Следующий прогон покажет в «Откуда пара» — «подтверждено вручную: …».

Если прогон нашёл пару иначе, чем подтверждено, в строке будет «подтверждено вручную; прогон … нашёл иначе: <путь>» — проверьте, какая пара верна. Неверную пару уберите из `confirmed.json`. Чтобы программа искала пары модели заново, удалите папку модели.

Если `confirmed.json` не читается (не JSON, чужой формат или версия), его пары не используются, а в сводке, строка «Библиотека», будет «confirmed.json: не прочитан (<причина>)». Запись с неизвестным номером `n` отбрасывается одна, с причиной там же.

## Возврат после автопоиска

После каждой настройки программа возвращает её по ONVIF и сверяет всю карту родного API с исходной. Строка «Возврат после автопоиска» — блокер: если камера осталась изменённой, в начале приложения «API камеры» стоит красная рамка с таблицей «параметр · где · было · осталось · как вернуть».

Способы вернуть, в порядке надёжности:

- **по ONVIF** — если у настройки есть пара и ONVIF её принимает;
- **запросом к родному API** — программа уже пробовала один раз: только для настроек изображения и только к значению из начала этого прогона; в рамке — запрос и что ответила камера;
- **в веб-интерфейсе камеры** — раздел, указанный в рамке.

Если прогон прервался посреди записи (камера пропала, программу закрыли), следующий прогон сначала разбирает журнал: возвращает настройку ONVIF, если значение ещё наше, а параметры родного API выводит строкой «Запись автопоиска соответствий API не завершена» (блокер) для ручного возврата — автопоиск на такой камере не начинается.

## Документ «Карта API»

Выпускается рядом с протоколом камеры (`api_map_<место>.pdf`, `.xlsx`, `.html`), если карта снята. На экране «Протоколы» — строка «Карта API» сразу после протокола своей камеры. Это справочный документ: итогов и подписей в нём нет, они в протоколе.

- `[*]` — параметр повторяется по каналам, профилям или потокам с одинаковыми допустимыми значениями; текущие значения — по индексам: «[0] 50 · [1] 50 · [2] 60».
- «скрыто» — пароль, ключ или токен: значение вырезано.
- «только описание» — раздел сети, учётных записей или безопасности: значения не читались и не сохранялись.
- «меняется сам» — значение менялось без записи (автоматика, счётчики); в сверке и автопоиске не участвует.
- Пометки «пара: …, API-MATCH-12» и «! расхождение с ONVIF» ведут в протокол камеры; «! не вернулось» — в рамку блокера.

Листы Excel: «Разделы» (класс, запросы, код ответа, сколько параметров, пар и расхождений), «Параметры» (строка на каждый параметр без свёртки: тип, минимум, максимум, шаг, допустимые, текущее числом и текстом), «Ошибки» (запросы, на которые камера не ответила, и запросы, остановленные программой).
